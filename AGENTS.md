# Contributing to the Job Applications Tracker

This file applies to the entire repository. Keep changes within the app's current scope: it is a single-user, local-first React/TypeScript application with no authentication, backend, synchronization, notifications, or collaboration layer.

## Repository map

- `src/App.tsx` coordinates shared filters, dialogs, imports, exports, persistence, and the eight views.
- `src/StageNotesPanel.tsx` is the stage prep notes panel and `src/StageNotePane.tsx` one stage's note inside it, with the ids tying a pane to its tab in `src/stageNoteIds.ts`. `src/views/PrepNotesView.tsx` is the view that hosts the panel, restores its arrangement and holds the empty state; `src/notesArrangement.ts` is what it restores from. `src/StageNoteEditor.tsx` is the Markdown editor, `src/FindWidget.tsx` the find bar, and `src/QuickOpen.tsx` the stage picker with its matching in `src/quickOpenMatch.ts`; `src/useDialogKeyboard.ts` holds the Escape and focus-trap behavior of the application dialog, which the prep notes panel no longer shares — it is a view, and a view is not dismissable.
- `src/markdown/` parses the supported Markdown subset into an AST and renders it as a foldable outline. `sections.ts` holds the section tree, the fold-key scheme, and the heading walks the outline and breadcrumbs read; `searchNote.ts` finds text in it. `capture.ts` and `correspondence.ts` derive a Markdown note from stored records so the renderer, the outline and the find work on them unchanged; `dayLog.ts` holds the day grouping they share, which is the only part of the two that must not drift.
- `src/correspondence.ts` turns stored messages into editor rows and mutation drafts, and
  `src/CorrespondenceFields.tsx` is the editor's correspondence section; `src/domain/correspondence.ts` is
  the direction configuration and the channel suggestions.
- `src/calendar/` reads the iCalendar subset that recruiter invites arrive in; `src/invites.ts` turns those
  events into editor rows and mutation drafts, and `src/InviteFields.tsx` is the editor's invite section.
- `src/StateHistory.tsx` renders the editor's read-only state history, with the spans it shows derived in `src/stateTimeline.ts`.
- `src/dateInput.ts` is the only place `datetime-local` wall time is converted to and from stored timestamps.
- `src/domain/noteEditing.ts` and `noteEditingPaths.ts` hold the client and pure halves of external note editing; `vite/note-edit-fs.ts` holds the filesystem and process side.
- `src/domain/` is the source of truth for types, state, rating and compensation configuration, mutations, validation, storage, IDs, and demo data.
- `src/backend/` is where the data actually goes. `types.ts` is the `TrackerBackend` interface; `serverBackend.ts` talks to the dev server's `/__db`, `/__attachments` and `/__note-edit` routes; `browserBackend.ts` is the static build's own storage, with `idb.ts` and `fileSystem.ts` as its two halves and `fakeDirectory.ts` the in-memory folder its tests drive it with. `index.ts` picks one, at build time, from `VITE_TRACKER_BACKEND`.
- `src/StorageStatus.tsx` is the static build's storage control and first-visit prompt. Both render nothing under the dev-server backend, which has no choice to offer.
- `src/domain/import.ts` turns the bytes of a chosen, dropped or pasted file into a validated document; `src/useFileImport.ts` is the window-level drop and paste listener that feeds it.
- `src/views/` contains view components and their derived-data helpers. `urgency.ts` scores and explains the ranking; `urgencyBands.ts` reads that ranking coarsely enough to band a sorted table, and is the only source for band ids, order and headings. A band is not a second ranking: it never changes a score, and the Urgency column still says on the row itself what the band is too coarse to.
- `src/test/` contains app integration and smoke tests; view-focused tests live beside the views.
- `src/styles.css` contains the responsive visual system. Spacing, radius, type size, colour,
  control height, shadow, and focus all come from the token scale in its `:root` block; reuse a
  token instead of adding a one-off value, and keep the media and container queries at the end of
  the file so a later base rule cannot outrank them. A query asks about whatever the rule actually
  depends on: touch target sizes are the device's business and stay in `@media`, while how the prep
  notes panel lays itself out is its own width and belongs in `@container panel`.
- `SMOKE_TEST.md` records the automated smoke coverage and optional browser-only checks.
- `src/test/panelHarness.tsx` mounts the prep notes panel for the browser suite. Shared because the
  mount is not incidental: the panel's height comes from the shell column above it, so a bare mount
  would size itself correctly whatever the chain above it did, and prove nothing.

Use pnpm for dependency and script commands. Do not introduce a second package manager or regenerate the lockfile with another tool.

## Core invariants

### States and transitions

- `StateId` is a closed union of exactly 19 states. `STATE_CONFIG` in `src/domain/states.ts` is the only source for state order and display labels.
- `classifyLifecycle` in `src/domain/states.ts` is the only source for whether a state is live, rejected or closed, and `LIVE_STATE_IDS` for the live set. It lives in the domain rather than in `src/views/urgency.ts` because the `live` state filter and the urgency ranking both read it, and two definitions of "still running" would let what a view shows drift from what it scores. Like `isRejectedState` it is a view-only grouping: it never restricts moves.
- The table opens sorted by Urgency, descending, which is also the only sort it bands under, so the headings are there before anything is clicked. It bands its rows only under that sort. A band is a coarse urgency reading, so under any other sort its headings would separate rows on a rule the visible order does not follow. A band holding nothing prints no heading.
- Inside a band the urgency score decides, except in `due`, which reads by date because its heading promises soonest first and the two disagree: each pressure decays over its own horizon, so an invite three weeks out can outscore a deadline next week. Preference is the last tiebreak and is never folded into the score.
- `live` is not a synonym for `not_rejected`. They differ over `accepted` and `no_openings`, which nobody turned down and nobody is still working, so both filter options exist.
- Preserve the configured labels exactly, including the em dashes in rejection labels.
- Name things `state` in code and stored data — `StateId`, `state`, `state_history`, `state_events`. Use
  "stage" only in copy a reader sees, where it reads more naturally ("prep notes for this stage", the Kanban
  stage columns). `stage_notes` predates this rule and stays as it is: it is a persisted field, and renaming
  it would silently canonicalize every existing note away on load. Note that `stagedFiles` in the attachment
  flow uses "stage" in its git sense, which is a third meaning — another reason not to reach for the word.
- Any state may move directly to any other state. Do not add a transition graph or broader pipeline stages.
- `rejectedStateFor` is a UI convenience that maps a live state to its rejected counterpart (`applied` → `auto_rejected`, otherwise `{state}_rejected` when that id exists). It must not restrict moves.
- A real state change updates `state` and `updated_at` and appends one timestamped `state_history` entry.
- Moving to the current state is a no-op: it must not update timestamps, replace the object, or append history.
- Editing unrelated fields updates `updated_at` but never appends state history.

### Application mutations

- Route creates, edits, moves, and deletes through the mutation functions in `src/domain/mutations.ts`; do not update application objects ad hoc in UI components.
- `commit` in `src/App.tsx` takes a mutation, not a document, and runs the queued mutations one at a time — each handed the document the write before it stored. Every write stores the whole document, so two built from the same snapshot do not merge: the second silently undoes the first. With the notes panel open that is routine rather than rare, because the autosave writes on a pause in typing while a captured line writes the instant it is entered. Queueing the mutation rather than the save is the part that matters: a mutation that has not run yet cannot hold a stale document. Do not add a `commit` overload that accepts a document, and do not read `trackerRef` to build one — a mutation reads the document it is given. `addApplication` takes an optional id for the same reason: an attachment folder is written under it before the application is stored, so the write stays one derivation rather than something assembled from a snapshot first.
- A note can be written from more than one place at once, and every such place must follow the document rather than trust what it last read. The notes panel seeds a draft per note as it joins, and afterwards adopts a body that changed underneath it — but only where its own draft still equals what it last wrote from there. Where the panel has unsaved keystrokes, those win: showing a stale body is recoverable, dropping what someone just typed is not. A compare card makes the same choice, gated on holding focus instead. Without the adopting half, the panel goes on showing the body it seeded and writes it back over the newer one on the next keystroke, which is how an edit made elsewhere disappears with nothing reporting a failure. `src/test/app.integration.test.tsx` holds the regression: a card edit, the full editor opened over it, and both sentences expected to survive.
- The external editor is the one concurrent writer with a channel of its own: the poll in `StageNotesDialog` reads the file, sets the draft, writes it, and marks it stored in one step, so the file coming back does not turn into a second write of itself. That poll is not a substitute for the rule above — it only covers notes it has a session for.
- `commit` writes nothing when a mutation returns the document it was given, and shows no notice for it either. Every mutation returns its input when there is nothing to do, which is what keeps a no-op move off the disk.
- IDs are immutable UUIDv7-compatible values generated when records are created. Company and role are editable attributes, not identity.
- A created application receives timestamps and an initial history entry for its starting state.
- `company` is required and non-blank. Optional text fields (`role`, `source`, `notes`, and similar) are canonicalized to strings or `null`; missing `source` on import canonicalizes to `null`.
- Stage prep notes hang off an application as `stage_notes`, at most one per `StateId`, stored in configured state order. A note may target any state, including one the application has not reached, because notes are written before a stage happens.
- A stage note `body` is raw Markdown text. Store exactly what was typed: no HTML is stored, generated, or injected, and the renderer maps the parsed AST to elements rather than using `dangerouslySetInnerHTML`.
- The dock is labelled **What they said** — `CAPTURE_SECTION` in `src/markdown/capture.ts`, with `CAPTURE_SECTION_IN_SENTENCE` for the labels that put it inside one. It names the contrast the dock exists for, the note above it being what you wrote before, rather than the act of writing it down, which the Capture button already has. The label is derived on render and never stored, so it can be changed without touching a note; the **field** is `heard` and stays that way, being a record rather than a caption.
- What you were told during a stage is `heard` on its stage note: `HeardEntry` records of `{ id, body, at }`, oldest first. It is a field rather than text inside `body` because the two are written at different moments by different hands, and because the day a line belongs to is then a reading of `at` rather than something parsed back out of a heading. `capturedMarkdown` in `src/markdown/capture.ts` renders the records as one note — a `###` heading per day, and a bullet per line stamped with the time it was captured — derived on render and never stored, so the reading view, the outline, and the find work on captures exactly as they do on a written note. It takes a day formatter and a time formatter rather than formatting either itself: how a date reads belongs to the view, and the day formatter doubles as what decides where one day ends. The stamp is a code span, so it reads as a record rather than as something that was said, and it carries no date — the heading above it already says which day this was.
- A capture is stored the moment it is entered, through `captureStageNote` or `updateApplicationStageCapture`. It is typed mid-conversation, where Escape and a closed tab are likelier than a deliberate Save; a record of what was said at a moment has no draft to roll back and no edit. Ids and `at` are minted in the mutation rather than supplied.
- A captured line is corrected through `reviseStageNoteCapture` or `reviseApplicationStageCapture`, which rewrite one line by id, or remove it when the new text is blank. `at` and the id do not move: an edit is a correction to what was written down, not a claim that it was said later, and the day a line reads under is a reading of that timestamp. Removing the last line from a stage that has nothing written for it drops the note, which is the rule a blank body already follows.
- Correcting is a mode of the dock, tracked in the panel as `editingLines` beside `editing` rather than in the pane, because the find has to know: a line in a box has no highlight to step onto, so its stage's captures sit out of the count exactly as a note in the editor does. Each row stores itself on Enter or on being left, and is keyed by id **and** stored body, so a row whose line has been stored starts again from it rather than holding a draft the store has moved past.
- `StageNoteDraft` carries no captures, so Save cannot write one twice or put one back. `applyStageNotes` preserves the `heard` of every stage it rewrites, and drops a note on a blank body only when that note holds no captures either: clearing what you wrote for a stage does not unsay what you were told in it. `heard` is absent-is-empty in validation, so documents written before captures existed load as valid documents with none.
- Route stage note changes through `applyStageNotes`, `setStageNote`, or `updateApplicationStageNotes`. A blank body removes that stage's note, an unchanged body is a no-op that returns the same object, and a rewritten body keeps `created_at` while refreshing the note's `updated_at` and the application's `updated_at`. Stage notes never append state history.
- Calendar invites hang off an application as `state_events`, each filed against one `StateId`, stored in
  configured state order and then start time. A state may hold several invites, and an invite may target a
  state the application has not reached. An invite may target any state; nothing about the invite decides
  which stage it belongs to.
- Route invite changes through `applyStateEvents`, `addStateEvent`, `removeStateEvent`,
  `updateApplicationStateEvents`, or `addApplicationStateEvent`. A blank summary drops that invite the way a
  blank body drops a prep note, an unchanged draft is a no-op that returns the same object, and a rescheduled
  invite keeps its `created_at` while refreshing its `updated_at` and the application's. Invites never append
  state history.
- `ics_uid` is the identity that makes re-importing safe: `addStateEvent` replaces the invite already holding
  that UID instead of appending beside it, keeps the `state` that invite was filed under, and ignores an
  invite whose `sequence` is behind the stored one. Two invites on one application may not share a UID.
- An invite must have a summary and a start; `ends_at` may be absent but may not precede `starts_at`.
- Hiring correspondence hangs off an application as `correspondence`, each message filed against one
  `StateId`, stored oldest first by the time it was sent. It is what was exchanged with the employer — a
  recruiter's email, a LinkedIn message, a rejection note, and what you sent back — and it is deliberately
  not a third mode of `stage_notes`. A prep note is what you wrote before a stage and `heard` is a line
  typed mid-conversation; a message is neither, because someone else wrote it at a moment you are only
  recording after the fact. A message may be filed against a state the application has not reached, and
  nothing about the message decides which stage it belongs to. The field is a mass noun and stays
  singular; there is no such word as `correspondences`.
- `at` is when the message was sent, and it is **supplied rather than minted** — you log on Friday what
  arrived on Tuesday, so a timestamp taken off the clock at the moment of filing would be a claim about
  your typing rather than about the conversation. It is the one required timestamp on a draft: a blank one
  is refused rather than stamped now, because stamping it now silently is exactly the dishonesty this
  record exists to end. It may also be **corrected**, which is where correspondence and `heard` part
  company: `HeardEntry.at` may not move because an edit there is a correction to what was written down,
  while a send time is a fact about the world you can simply have got wrong. `created_at` is when you wrote
  the record and never moves. Both are stored because they answer different questions, which is also why
  `HeardEntry` and `CompletedAction` need only one timestamp each.
- `direction` is `received` or `sent` and has no third value. Half of hiring correspondence is what you
  sent, and a log holding one side reads as a mystery; anything that is neither — a thought about the
  process, a reminder — is `notes` or a prep note, and a third direction would reopen the misuse this
  record was added to end. `CORRESPONDENCE_CONFIG` in `src/domain/correspondence.ts` is the only source of
  the two ids, their labels and their order, the way `RATING_CONFIG` is for dimensions.
- `who` is the other person — the sender of a message received, the recipient of one sent — and may be
  absent. `HeardEntry` deliberately has no author and that is not a contradiction: a captured line comes
  from the room its stage note already names, and asking who was speaking is a question to answer
  mid-interview. A message has exactly one correspondent, it is in the header you are copying from, and a
  log mixing a recruiter, a coordinator and a hiring manager cannot be read without it.
- `subject` is what the message was about, and may be absent: a LinkedIn note or an SMS has
  none, and those are exactly the messages whose first line is its own summary. Where it is
  present it is **also the thread** — messages sharing a subject within a stage are the same
  conversation — which is why there is no separate thread id to keep in step with it. It goes
  in `search_text`: it is the most searchable thing about a message.
- The log puts one `####` heading over a **run** of messages sharing a subject, rather than
  restating it on every row. Grouping, never reordering: the log stays in send order, so two
  threads answered in turn read as they happened and a subject simply comes back when the
  conversation does. A message with no subject ends a run and opens none of its own. Because
  the heading is a fold, a thread folds as one.
- The day grouping stays the outer spine, so a thread spanning days shows its heading under
  each day it has messages in. That is the cost of keeping the log chronological, and it is
  the right way round for a log: each day reads on its own. Making the subject the spine
  instead would read as a mailbox rather than as what happened when.
- The editor groups its rows the same way and on the same rule, through `opensThread`: one
  line over a run of rows sharing a subject inside a stage. The line goes **between** the rows
  rather than wrapped around them, so the list stays flat — a message's number is its position
  in it, and a name must not move because the message above it was given a subject.
- With the subject on that line, a row summarises itself by its **body**, which is the split
  the log already makes. Three rows each reading "Next steps" under a heading reading "Next
  steps" would say nothing about which is which.
- `channel` is free text with `CHANNEL_SUGGESTIONS` behind the editor's picker, the arrangement `source`
  already keeps: the picker curates the vocabulary and widening it must never narrow what import accepts. A
  closed union would be wrong the first time a message arrives by SMS, and there are no migrations here
  that could widen one later. Unlike a currency it is not case-folded — `LinkedIn` is a name, not a code —
  so `email` and `Email` are two values, exactly as they already are for `source`.
- A message's row in the editor is **folded to one line** until it is the one being worked on.
  A message is six controls and an email; five of them came to four screens of a dialog whose
  job is the application, not the thread. The line is `correspondenceRowSummary` — when, who,
  how, and a line of what it says — and it is the row's accessible name, because the summary
  is what tells two messages apart while a number says only where in the list you are. A row
  just added arrives open, since it is the one you are about to fill in.
- That line is cut by the same `preview` the log's folded row uses, and names its sender
  through the same `correspondenceSender`. A row that summarised a message one way in the
  editor and another way in the panel would read as two different messages. `preview` lives in
  `src/markdown/preview.ts` rather than inside the renderer for that reason — and because a
  component file exporting it costs the whole file its Fast Refresh.
- Correspondence stays in the application editor rather than moving to a view of its own, and
  the prep notes precedent does not transfer. A note is a document you compose over time, typed
  mid-interview, which is why the panel autosaves and has no Save at all. A message is entered
  once, complete, from a paste, at a keyboard — a record with fields and a date filed against a
  stage, which is what `InviteFields` already is. What made it feel wrong in the editor was one
  enormous field, and that is a rendering problem rather than a home. A view would earn its
  place by showing correspondence **across** applications, which neither the editor nor the
  dock does; that is a feature with its own argument, not a consequence of a tall form.
- Each thread carries its own **Add**, beside its subject, through `newThreadRow`. It takes
  everything that makes a message part of that conversation — the subject, the correspondent,
  the channel, and the **thread's** stage rather than the application's current one, since a
  shared subject in another stage is a different thread by the rule the grouping keeps — and
  leaves the two things you are there to write. The row lands inside the run rather than at
  the top of the list: anywhere else it would open a second heading saying the same words. Its
  visible label is just "Add", with the subject in its accessible name, because a subject can
  be a sentence and every thread carries one of these.
- **Add message** at the foot of the section stays the way to start a conversation, and seeds
  the new row's correspondent and channel from the newest row that has
  either, through `newCorrespondenceRow`. A hiring conversation is one recruiter on one
  channel far more often than not, so re-typing both for every message asks the reader to
  restate what the row above already says; both stay editable, so a thread that does change
  hands costs one correction. Nothing else carries forward — not the text, not the time, and
  not the direction, because a reply follows a message rather than another reply. Read off
  the rows rather than the stored log, since a message just typed is the likeliest thing the
  next one follows.
- Direction is two radios rather than a select: a menu costs two interactions to choose
  between two things, and both are worth seeing without opening anything. Radios rather than
  buttons carrying `aria-pressed`, because this is a choice between options and the platform
  already has a control that says so, arrow keys included. The group is named per row, or two
  messages on screen share one group. The date field is **Date sent**, not "Sent", which is
  one of the two directions a line above it.
- Route correspondence changes through `applyCorrespondence` or `updateApplicationCorrespondence`. A draft
  carrying an existing id keeps that record's `created_at` while its `at`, direction, channel,
  correspondent and text are all rewritten from the draft; a blank body drops the message, which is how the
  editor removes a row; an unchanged list returns the same object. Correspondence never appends state
  history, and like `ratings`, `stage_notes` and `state_events` it is absent from `ApplicationEdits`. There
  is deliberately no append-one mutation: unlike a capture it is composed after the fact with a date and a
  direction to choose, so it is a form with a Save, and unlike an invite it has no calendar UID forcing a
  replace-or-append decision. Add one only alongside a control that logs a message from outside the editor,
  since that caller has no draft list to extend.
- Correspondence is stored in send order — `at`, then id — rather than in configured state order the way
  invites are. Invites are read one stage at a time and their times and stages agree by construction; a log
  is read as a timeline, and the stage a message is filed under does not predict when it was sent, since a
  coordinator apologising for the delay on Interview 1 arrives after the Interview 2 invite.
  `sortedCorrespondence` in `mutations.ts` and `correspondenceValue` in `validation.ts` must sort by the
  same rule and both must fall back to the id: the validator rebuilds the array in file order, so without
  the tiebreak a document comes back in an order it was not written in and every no-op-by-identity check
  downstream reports a change that did not happen. Compare by parsed instant rather than by string, because
  this is the first `at` a person supplies and one written with an offset does not sort lexically.
- Logging a message refreshes the application's `updated_at`, which is the honest answer — you did touch
  it. It appends no `state_history`, so the silence `daysSinceLastMove` measures is untouched and neither
  the urgency term nor Idle moves: writing down an email that arrived last week is not the employer
  answering you. It never enters `urgencyFor`, the score, or band placement, the same fence Idle and
  preference sit behind. A message is something that already happened, and the ranking carries what is
  still owed.
- A next action may have no date. A date may not survive without a non-blank action.
- A next action is resolved through `completeNextAction`, not by hand-clearing the field: it nulls `next_action` and `next_action_at` and appends the task to `completed_actions`. A blank action returns the same object, `deadline_at` is untouched because an external closing date is not the task, and completing an action never appends state history.
- `completed_actions` holds carried-out next actions as records, oldest first, and is deliberately **not** appended to `notes`. The two are written differently — `notes` is prose you compose and revise, a completed action is one line the app writes the instant Done is pressed — so mixing them means neither can be edited without disturbing the other, the date has to be parsed back out of prose, and a Done pressed by mistake cannot be removed cleanly. This is the same argument `HeardEntry` already makes for captured lines.
- Route completed action changes through `completeNextAction`, `applyCompletedActions`, `completeApplicationNextAction`, or `updateApplicationCompletedActions`. Like `ratings`, `stage_notes` and `state_events`, `completed_actions` is absent from `ApplicationEdits`, because a second write path would destroy per-record ids and timestamps. A draft carrying an existing id keeps that record's `at`; a blank action drops the entry, which is how the editor removes a mistake; an unchanged list returns the same object.
- Removing a completed action does not restore the next action. Undoing the record is not the same as undoing the work, and guessing which one was meant would be worse than doing neither.
- Moving into a rejected state drops an outstanding `next_action` and `next_action_at` as part of the move. A rejection ends the application, so a task still on it is work that will not happen, and left alone it accumulates: nothing ever asks about the follow-up again. The task is dropped, never routed through `completeNextAction`, because `completed_actions` means carried out and an abandoned task was not. The history entry for the move is the record of why it went, and `deadline_at` survives for the same reason it survives a completion. Only `isRejectedState` destinations, not every ending: a task on `accepted` is live work, and `no_openings` is a state you may still be working since nothing was turned down. Setting a new action after a rejection still works; only the move clears one.
- `ratings` holds at most one judgement per dimension, in `RATING_CONFIG` order. Three states are distinct and all meaningful: no record means never assessed, `score: null` means asked and genuinely cannot tell, and an integer 1-5 is a judgement. New applications start with no records.
- Route rating changes through `applyRatings`, `clearRating`, `updateApplicationRatings` and `clearApplicationRating`; `ratings` is deliberately absent from `ApplicationEdits`, like `stage_notes` and `state_events`, because a second write path would destroy per-record `created_at`. An unchanged draft returns the same object, a rewritten score keeps `created_at` and refreshes both `updated_at`s, and ratings never append state history.
- Unlike a stage prep note, a rating has no blank form that could mean "remove this" — `score: null` is a real judgement. So a draft absent from the array leaves its dimension untouched and removal is an explicit `clearRating`.
- `RATING_CONFIG` in `src/domain/ratings.ts` is the only source of dimension ids, labels and order. A dimension belongs there only if two reasonable people could rate the same fact differently, which is why compensation is not one: given a number, more is always better, so it is a measurement and belongs in its own field.
- `compensation` is that field. It holds one currency plus three nullable bands — `advertised`, `expected`, `offered` — in `COMPENSATION_CONFIG` order. All three are stored rather than one current value because compensation moves and the progression is the point; overwriting would erase it. New applications start with an empty record, never a missing one.
- Every figure is a band. A point value is a band whose ends match, which keeps one representation instead of two and spares every reader a `max === null` branch. Both ends are annual gross base pay as whole positive integers: cents never decide a job, and zero is not a figure you were quoted — `null` already says that.
- One currency covers the whole record, not each band: one application is one employer discussing one salary, and letting the stages disagree would make the progression meaningless. It is a three-letter code stored upper case. Any three-letter code is accepted on import and by the mutations; no conversion is attempted anywhere in the app.
- The editor offers currencies as a picker built from `CURRENCY_SUGGESTIONS`, so it creates only listed codes — add one there to offer it. The list must always include whatever the record already holds, which `currencyOptions` enforces: a picker that silently dropped an unrecognised code would rewrite the amounts' unit on the next save. Widening the picker is a UI decision and must not narrow what import accepts.
- The amount boxes step by `AMOUNT_STEP` on the arrow keys and `AMOUNT_STEP_LARGE` with shift, through `steppedAmount`. They stay `inputMode="numeric"` text boxes rather than `type="number"`, which refuses the thousands separators people actually type. A step that cannot be taken returns `null` and the key is left alone, so an unusable box still behaves like a text box instead of swallowing the keystroke.
- A currency may not survive without an amount — the same rule as a next-action date and a blank action, and canonicalized the same silent way. The reverse is an error, not a drop: a number whose unit is unknown cannot be read at all.
- `expected` is both what you are aiming for and the target the other two are measured against. There is deliberately no global target: the document shape is closed and discards any extra top-level key, so there is nowhere honest to persist one, and one number could not be compared against a per-application currency anyway. What you would accept genuinely differs by role, level, and country, so it belongs on the application.
- `compensation` is in `ApplicationEdits`, unlike `ratings`, `stage_notes`, and `state_events`. It carries no per-record timestamps, so there is nothing a second write path could destroy: the whole record is replaced at once, exactly the way `deadline_at` is. Do not add per-stage timestamps — `state_history` already records when `offer` was reached, and the stage names carry the rest of the story.
- `deadline_at` is an external fact (a posting closing, an offer decision date), not a planning date. It is independent of `next_action`: it may be set with no next action, and clearing the next action must not clear it.
- Application timestamps and history timestamps are timezone-qualified ISO-8601 strings.

### Persistence, import, and export

- Missing `completed_actions` canonicalizes to `[]` on import — a document written before Done existed is valid, not broken. Reject a blank action, a malformed timestamp, and duplicate ids within one application. Entries are stored sorted by `at`.
- Missing `ratings` canonicalizes to `[]` on import. Reject an unknown dimension, two ratings for one dimension, and any score that is not `null` or an integer from 1 to 5.
- Missing `compensation` canonicalizes to an empty record on import. Reject a currency that is not three letters, an amount that is not a whole positive integer, a band whose `max` is below its `min`, and an amount with no currency. A currency with no amount behind it is dropped rather than rejected.
- Two backends implement `TrackerBackend`, chosen at build time in `src/backend/index.ts`. The dev server is the default; `VITE_TRACKER_BACKEND=browser` selects the static one. Reach either through the existing names in `src/domain/{storage,attachments,noteEditing}.ts` — those are thin dispatchers, and call sites should not know which backend answered. New persistence work goes on the interface, not into one implementation.
- The static backend saves into IndexedDB on every change, and additionally into a folder the viewer connected through the File System Access API. The two are not alternatives: the folder is the copy that outlives the browser profile, and the IndexedDB copy is what stops a permission the browser revoked — which cannot be renewed outside a user gesture — from taking the data with it. Never drop one write in favour of the other.
- A connected folder holds `tracker.json` at its top and attachments under `attachments/{applicationId}/{attachmentId}`: the same layout the dev server writes, so one folder opens in either build. Connecting adopts what the folder already holds rather than overwriting it.
- Connecting and reconnecting move data in opposite directions, and the difference is not cosmetic. Picking a folder adopts its contents: it is how someone opens last week's export. Regaining a lapsed permission on the folder already stored pushes browser storage into it, because the browser copy kept taking writes while the folder's stopped — reading the folder there would replace however long someone spent typing with the older file and report it as a success.
- Backend writes are serialized inside the backend, not only by `App.tsx`'s commit queue. Two saves built from one snapshot do not merge, so the slower landing last silently undoes the newer one.
- Persist one self-describing JSON database file with shape `{ schema, applications, indexes }`. The live app uses `data/tracker.json`; the demo profile uses `data/demo/tracker.json`. The embedded `schema` object is the current JSON Schema; update it when the shape evolves instead of running migrations.
- `applications` is the source of truth. Rebuild `indexes` on every successful load or save when they are missing or stale. Do not hand-edit indexes; edit `applications` or go through mutations.
- Seed an empty live document when `data/tracker.json` is absent. Seed demo data only for `data/demo/tracker.json` when that file is absent, via `pnpm dev:demo` or `pnpm start:demo`. A valid saved document—even an empty one—must not be reseeded on reload.
- Validate and canonicalize an imported document before confirmation or replacement. A parse error, validation error, unsupported legacy `schema_version`, or cancelled confirmation must leave saved data untouched.
- Import still accepts legacy `{ schema_version: 1, applications }` exports. Canonicalize applications, attach the current schema, and rebuild indexes.
- Ignore unknown imported fields for forward compatibility. Reject duplicate IDs, invalid states, malformed timestamps, invalid URLs, and supplied history whose final state differs from the current state. Missing `state_history` is accepted for compatibility and synthesized from the current state; supplied history must be non-empty.
- Import replaces the entire collection; export writes a zip archive with `tracker.json` plus attachment files. Legacy JSON import still works without files.
- A file can arrive by button, by drop anywhere on the window, or by paste, and all three go through one path: `readTrackerImport` in `src/domain/import.ts` turns bytes into a validated document or a list of `ValidationError`s, and `importFile` in `src/App.tsx` is the only thing that persists one. Validation happens before the confirmation, so the question names what is in the file and an unreadable file never asks it. Do not add a fourth entry point that parses bytes itself.
- `useFileImport` acts only on drags whose `dataTransfer.types` lists `Files`. The board drags cards and the notes panel drags tabs; a window listener that did not check would throw an overlay over the column a card is aimed at. Pasted *text* is never an import — the listener is on the window and sees every paste in the app, including the ones into a note.
- Missing `stage_notes` on import canonicalizes to `[]`. Reject blank bodies, invalid states, and duplicate states within one application.
- Missing `state_events` on import canonicalizes to `[]`. Reject blank summaries, invalid states, malformed
  timestamps, an end before the start, a non-http(s) link, a negative sequence, duplicate ids, and duplicate
  calendar UIDs within one application.
- Missing `correspondence` on import canonicalizes to `[]` — a document written before the log existed is
  valid, not broken. Reject a blank body, an invalid state, an unknown direction, a malformed `at`,
  `created_at` or `updated_at`, and duplicate ids within one application. A blank channel or correspondent
  is dropped to `null` rather than rejected. There is deliberately no rule ordering `at` against
  `created_at`, and none rejecting a future `at`: a message logged days after it arrived is the ordinary
  case, and a rule enforced against the clock would be wrong in another timezone.
- Application attachments store metadata on each application and file bytes under `{dataDir}/attachments/{applicationId}/{attachmentId}` (`data/attachments/` live, `data/demo/attachments/` demo). Missing `attachments` on import canonicalizes to `[]`. Add and remove attachments through mutations; cap each file at 25 MiB.
- Keep view-only values derived. Never persist Kanban columns, idle status, date groups, stage durations, statistics, or filters. Do not persist overdue/upcoming buckets or band membership because they depend on browser-local "today". Idle is named here explicitly because it reads like a status worth storing and is not: it is a function of today, so a stored flag would be wrong on the next day, in another timezone, or on a machine whose clock differs.
- On first launch after upgrading from browser storage, migrate a valid legacy `localStorage` document into `data/tracker.json` once (live profile only), then stop using `localStorage` for the document. The static build skips the migration entirely: the legacy key is not its storage, and it must not adopt a document it never wrote. `localStorage` still holds per-machine interface state and only that: the theme, and the prep notes arrangement in `src/notesArrangement.ts`. Neither is the reader's data, neither belongs in an export, and the arrangement in particular would rewrite the shared file on every tab click if it were stored there. Its key carries the tracker profile, so a demo session cannot hand its refs to a live one.
- A stored arrangement is reconciled against the document on the way back in, never trusted: `restoreArrangement` drops tabs whose application is gone, tabs naming something `isStateId` does not recognise, and a note that was somehow stored in two panes; it clamps a pane below `MIN_PANE_FRACTION`, prunes what emptied, and returns null when nothing is left — which is the view's empty state. A tab whose *note* was emptied is deliberately kept. The panel's pane counter starts at `highestPaneNumber` of what was restored, or minting would hand a second pane an id a restored one already holds.
- The static build opens on an empty document, never on demo data. Someone arriving at the hosted site is there to enter their own applications, not to clear out nineteen fictional ones first. The demo profile is the exception and seeds its nineteen examples, matching what the dev server does for an absent `data/demo/tracker.json`. Seed only when nothing is stored: an emptied demo stays emptied.
- The demo and the tracker are served from one origin, so nothing but the IndexedDB database name separates their storage. `idbName` in `src/backend/idb.ts` is the only place that separation lives; keep it keyed on the profile.
- Derive links between the two hosted builds from `import.meta.env.BASE_URL` through `src/siteLinks.ts`. A fork is served from a different repository name, so a hard-coded path is wrong everywhere but here.
- External note editing starts a process on the machine running the dev server, so the static build cannot offer it. Gate it on `backend.capabilities.externalEditor` rather than on the profile or on feature detection at the call site.
- A Cursor `beforeSubmitPrompt` hook backs up live and demo `tracker.json` files and their attachment directories to `data/backups/{timestamp}/` before agent prompts. Agents should edit applications through mutations and attachment APIs; do not bypass the backup hook with alternate write paths.

### Demo data

  within an application, a loose note sitting beside a threaded conversation, and an offer negotiation —

  Both are load-bearing rather than decorative: a log of one-liners exercises neither the folded row nor
  Read, which is most of what the reading side is. First lines sit either side of the preview's 48

A test in `src/views/compensation.test.ts` asserts it; if you retune a seed's amounts, check that no cell shape stops appearing.

That is the only seed where silence and last-touched disagree: the urgency reason reads it as no stage change while the Kanban card and Activity column read it as Idle. Keep a seed with that shape, or the difference between the two measures goes untested in the demo. Its stage move sits past `IDLE_THRESHOLD_DAYS` on purpose — it is also the only seed that is Idle, so shortening that silence leaves the pill, the Activity column and the activity filter with nothing to show.

### View behavior

- The topbar has two sides: where you are, and what you can do. The view strip and the prep notes toggle share the left cell, divided by a hairline so the toggle does not read as an eighth item in the strip; the action cluster on the right is theme, `Add application`, overflow, and ends on the primary button. The toggle does not belong there — it changes which surface you are on rather than doing anything to the collection, it is `aria-pressed` and lights up, and lit beside a filled accent CTA the two would compete for the same glance. Under 1000px the whole left cell drops to its own row: place it by the cell, never by the strip inside it, which is a flex item there and takes an `order` while ignoring a grid placement.
- One context bar under the topbar carries the view title, the filtered count, and the global
  filters. The active view's name is the page `h1` for document structure only — the nav tab
  already shows it, so no view repeats it as a visible heading. Table and Statistics keep
  their `h2` as `sr-only`. Statistics' visible **Stages**, **Sources** and **Ratings** `h3`s are section headings inside the view, not the view's name,
  so it does not break that rule.
- Import, export, and demo reset live behind the topbar's **More actions** disclosure. It is a
  disclosure holding plain buttons, not an ARIA menu, so Tab alone reaches the items; keep Escape,
  outside-click dismissal, and focus return to the trigger. The import file input must stay mounted
  outside the panel, which unmounts when it closes.
- The Kanban card's state `<select>` reads **Move** rather than repeating the lane's state, and is
  laid over that trigger at zero opacity. It must remain a real focusable `combobox` named
  `Move {company} to state` — it is the accessible and touch fallback for drag-and-drop.
- All four views in the strip consume the same application collection and respect app-wide search, state, company, and source filters. **Prep notes** is not one of them and is not in the strip: it is reached from the header, beside Add application, because it is a workspace rather than a slice of the collection and it takes the unfiltered set. Its tabs are the reader's own arrangement, and a company filter would empty a workspace assembled across several applications — a note being written is not something a filter over the board may take away. The header button says so plainly when the workspace is up — accent fill, accent border, the label in bold — rather than by a shade of quiet: it is a layer over a view rather than one of the views in the strip, so it cannot borrow their underline, and a button that looks the same open as shut answers the one question it is asked, "am I in there", with nothing at all. It is a layer over whichever view you are on rather than a view of its own — a `notesOpen` flag beside `activeView`, deliberately not a `ViewId` — so the view underneath does not change while the notes are up and putting it back when they go needs nothing remembered. The header button is a toggle and carries `aria-pressed`, not `aria-current`: pressing it again takes the notes away and leaves Table, or Kanban, or whatever was there. Picking a view from the strip is the other way out, because a tab that changed only what was underneath would look like a button that does nothing. While the notes are up no tab in the strip is `aria-current`: what is on screen is the workspace, not the view it was opened over.
- The context bar carries what the view it names can be asked. On the seven it is the count, the search and the filters, all of which act on the collection. On Prep notes those would be controls that do nothing over a number that means nothing — and with them gone the row held only the word already lit in the header button, so the bar is not rendered there at all. The `h1` stays, `sr-only`, because the page still owes a screen reader its name; the line it was taking goes to the notes, on every window open. A test scoping itself to that row must look it up where it uses it: a scope captured before a visit to prep notes is a detached node afterwards, and typing into one fails silently. The search that makes sense here is over the notes, and it lives in the sidebar with the tree it filters rather than in a bar above it — beside what it searches. That is a third search and deliberately distinct from the two that exist: the global search asks which *applications* match and returns rows, the panel's find steps through the notes already open, and this asks which notes hold the words and opens the one picked.
- The state filter takes a single state or one of two outcome groups, `rejected` and `not_rejected`. `StateFilter`, `stateFilterMatches` and `statesForFilter` in `src/domain/states.ts` are the only source for what each admits; the Kanban's `visibleStates` comes from the same helper. The groups share the state control rather than adding one beside it, because pairing them with a single state selects nothing.
- `isRejectedState` lives in `src/domain/states.ts` and derives from `rejectedStateFor`, so it stays in step with `STATE_CONFIG`. `no_openings` and `accepted` are not rejections.
- The source filter lists only sources applications actually carry, not `SOURCE_SUGGESTIONS`: an unused suggestion would filter to nothing.
- Copy roles writes the roles of the filtered collection, deduplicated, one per line. It copies what is showing, so narrowing the filters is how you narrow the copy.
- `onCompleteAction` is required on `ApplicationsViewProps` rather than optional, so a new task-bearing view cannot silently forget to wire it. Views with no task row simply ignore it.
- Table column filters further narrow only the table. They are display state and must not be persisted.
- The table's Invites column lists every invite on an application, soonest first, with a cancelled one marked
  in words as well as struck through. Its filter matches summary, location, date, and the word "cancelled" —
  so it reaches past invites the column shows but the Kanban card does not. Sorting the column sorts by the
  next invite still ahead, which sinks rows with nothing coming to the bottom ascending.
- **Reject** moves a live row to `rejectedStateFor` its current state, from the table only, through the one `RejectButton`. It renders nothing on a finished row — a rejected application has nowhere left to go, and `accepted` and `no_openings` have no counterpart — and its accessible name says which state it moves to, so a screen reader hears the outcome rather than a column of identical buttons. It is a shortcut, not a capability: the state select beside it reaches the same state, and must keep doing so. It is styled quietly rather than as `--danger`, unlike the Stale view's version it replaces: recording that somebody turned you down is an ordinary move, not a destructive act.
- **Done** resolves a next action from the Kanban card and the table's next action cell, through the one `CompleteActionButton`. It renders nothing when there is no action — a disabled control on every untasked row is noise — and its accessible name states the task, so a screen reader hears which one is closing rather than a column of identical buttons. Both surfaces carry it because the table is where tasks are worked through and Kanban is the default view.
- On the Kanban card, Done sits on the action line beside the task it resolves, not in the card's footer row — that row holds controls that act on the whole card (Move, Prep notes), and Done acts on one line of it. The label spans on the card carry `application-card__label` rather than being matched as bare descendant spans, because the action line now holds a button whose text must not shrink to label size.
- The editor resolves an action through the same record, but as a draft: **Done** on the Next action field's own row clears the draft action and adds a row to **Completed actions**, and nothing is written until the dialog is saved. Every other control in that form behaves this way, and an immediate write would commit while other edits sit unsaved beside it. The section below lists what is recorded, newest first, apart from the Notes textarea, and each row can be removed.
- `.next-action-field` is one full-width row holding the action, its date, and then Done, in that order: the control follows the fields it acts on rather than sitting between them. The action takes the free space, the date and button keep their intrinsic width, and `align-items: end` lines all three up on the inputs rather than on the labels above them. The button is a sibling of the labels, not a child of one: a label hands its click to the first labelable element it wraps, so nesting an interactive control inside makes which one you hit depend on the browser. Its visible text is **Done**, matching the row, card and table controls; the accessible name is `Mark next action done`, because "Done" alone does not say what it finishes. An integration test asserts the DOM order, not just that the three sit together.
- The application editor shows `state_history` as a read-only **History** list, oldest first, so the order tells the story and the current state sits beside the State select that changes it. It renders only when editing: a new application has no history, and a state picked but not yet saved is deliberately absent because the list is the saved record.
- Each entry shows how long that state held — the gap to the next move, or to now for the last one. Spans are derived on render in `stateTimeline`, never persisted, and counted in browser-local days like staleness, so two moves on one day read as `Same day` rather than a rounded fraction.
- Stage prep notes are a top-level view, reached from the tab strip or from the Kanban card and the table row — which navigate to it rather than opening a dialog over it. What is open, how it is split, how wide the panes are and which tab is showing survive the app being closed, because the workspace is the point of a panel holding several applications at once. Arriving from a card opens only the note asked for; the fan of an application's current stage and its other noted stages (`openingLayout`) applies when there is no arrangement to restore, or every visit would pile that application's stages back up. The panel holds notes from **any application, not just the one it was opened from**: a tab is a `NoteRef` — an application and a state — and `Ctrl+P` reaches every application's notes. It opens on the application it was invoked for, that application's current stage first and then its other noted stages, so the stage you are interviewing for is the one you land on. Global search matches stage note text through `search_text`.
- A message's header line names its **sender**, not its direction: `You` for one you sent, the
  correspondent for one you received, and `Them` when none was recorded — because a received
  message with no name on it must still not read as yours. A log holding both sides has no use
  for the word "Sent" on every other row, and naming the sender says the same thing in space a
  name was taking anyway. This is what every mail client does with "me".
- The messages in the dock read **open**. You went to the section to read them, and a press per
  message before any reading starts is a toll on the common case. **Collapse all** is one press
  the other way, and the strip's cap means a long thread scrolls rather than swallowing the
  prep note above it — **Read** is the answer when it needs the column.
- Whether a record starts folded and whether a log **summarises** its folded records are two
  props, not one: `collapseInitially` and `summariseFolds`. They were one while the messages
  started folded, and separating them is what let the default flip without quietly losing the
  summary the moment a reader pressed Collapse all.
- `summariseFolds` also decides what "all" means to the fold-all control — the records, not
  every fold, since folding a log's day headings away leaves dates with nothing under them.
  It is off for notes on purpose. Folding a point in a note **you wrote** is a deliberate act of
  putting it away, and previewing it would undo the thing you just asked for; you know what is
  under there. Do not extend the preview to notes.
- **Read** gives the messages the pane instead of the strip at the bottom of it, and swaps
  back to the prep note. Folding made the log scannable, which is what a strip is for; it did
  nothing for the message you then open, which is a whole email read through an 11rem window.
  The note is hidden rather than squeezed — a pane split between a prep note and a long email
  serves neither, and the note is one press away with its scroll intact. This is deliberately
  two states rather than a drag handle: a handle trades the two by degrees, and what a long
  email wants is the column, while what you want back afterwards is the note, whole.
- The two dock selectors — `.panel__notes .stage-note > .stage-note__dock` and its
  `--reading` counterpart — carry **the same specificity**, three classes each, so source
  order is the only thing deciding between them. The override must stay after the cap it
  undoes or the dock silently keeps its 70%, which looks close enough to working to survive a
  screenshot. A test in `src/test/styles.test.ts` pins the order and one in
  `src/correspondenceDock.browser.test.tsx` measures the result.
- The written note is hidden while the messages hold the pane, so the find hands the pane back
  when it steps onto a match in the note — the same rule, and the same reason, as a match
  inside a collapsed section, and from the step handler rather than an effect.
- **Read** opens the messages on the way in, because pressing it is saying "I am reading this
  now" and a press per message would make that a second job. It waits for the log's fold
  controls rather than firing on the press — Read opens the section too, so the log is not
  mounted in the render that starts it — and latches, since the controls arrive new whenever
  anything folds.
- A **bulk open reaches everything**, quoted chains included: Read opens exactly as far as
  Expand all, so there is one rule for what opening the lot means rather than two. A chevron
  opens the thing it is on and nothing inside it, which is what keeps a quoted chain shut
  when you open the one message you wanted — the distinction is between opening everything
  and opening one thing, not between kinds of fold.
- The section has its own **Collapse all**, the way the prep note does, handed up through
  `onFoldControls` and drawn in the row that names the section rather than inside the column
  it would scroll away with. It is kept apart from the note's controls: two logs on screen and
  a button that folded whichever reported last is a button nobody can predict. The note's own
  fold control is withdrawn while the messages have the pane — the note is hidden then, so
  folding it would appear to do nothing, and two buttons reading "Collapse all" at once are
  told apart only by their accessible names.
- What "all" means to that control follows `summariseFolds`. In a note it is every fold,
  which leaves the bare outline that is the whole use of it there. In a log it is the records
  only: folding the day headings away leaves two dates and nothing under them, neither
  readable nor scannable.
- A quoted reply starts shut and stays shut when its own message is opened by its chevron. In
  a log that keeps both sides, the quoted chain is the message above quoted back — duplicate
  by construction — so a log that arrived with every one of them unrolled would be unreadable.
  Opening the lot deliberately is another matter, and reaches them.
- The section a reader sees is called **Messages**, through `CORRESPONDENCE_SECTION`. The stored
  field stays `correspondence`: renaming it would be a migration, and this document runs none —
  so the code says correspondence and the interface says messages, deliberately.
- Every control in the dock's section row is one height, through `align-items: stretch` on
  `.stage-note__dock-row`. Matching their `min-height` floors does not do it: the toggle carries
  a count badge with padding of its own, so the row's height comes from content rather than from
  the floor either of them declares.
- A pane's dock holds two collapsible sections, both collapsed by default: **Messages** above, then
  **What they said**. They read in that order down the pane, and the find numbers them in that order after
  the written note — `matchBase`, then `correspondenceMatchBase`, then `heardMatchBase`. Only the captures
  have a carve-out (lines open for correcting sit out, each being in a box with no highlight to step onto);
  correspondence cannot be written from the panel at all, so no mode of it leaves one of its matches with
  nowhere to send a caret. Both sections are counted whether or not they are open, so stepping onto a match
  opens the section holding it — from the step handler, never from an effect on the cursor, which moves on
  every keystroke in the find box.
- A Kanban card carries a **Messages** button beside its prep notes one, through
  `MessagesButton`, showing how many the application holds. It opens the **form**, not the
  panel — the button beside it already reaches the panel, a card is one application, and the
  panel reads one stage at a time, so the form is the surface holding the whole log and the
  only one that can write it. It lands on the card's own stage, which is the conversation most
  likely to be live, reusing the `messagesFor` the dock's Edit messages already passes.
- The panel **reads** correspondence and does not write it. A message carries a send time you
  supply and a stage you file it under, and `dateInput.ts` is deliberately the only place wall
  time becomes a timestamp — a conversion that belongs in a form. What the dock offers instead
  is **Edit messages**, which opens the application's form with that stage's rows already
  unfolded and scrolled to, through `messagesFor` on the editor. Landing at the top of a long
  form to hunt for the row you were just reading was the whole of the annoyance; the form was
  never the wrong place to write in.
- Arriving that way **focuses the section's own name**, not the form's first field. The dialog
  autofocuses that field otherwise, and focusing an element scrolls it into view — so a scroll
  on its own is undone a frame later, which is what made the first attempt at this look like it
  had done nothing. Landing on the name also gives a screen reader somewhere that says where it
  is, rather than dropping it into a textarea mid-form. The name is focusable programmatically
  only: nobody tabbing through the form should stop on a label.
- `messagesFor` unfolds once, on the way in. Re-running it would drag the reader back to the

  Opening the application from the subject line passes none, so the rows stay folded: that is
  the form, not a way back to one row of it.
- The button is named **Edit messages in {stage}**, which contains its visible label so voice
  control can reach it. That collides with a loose `/^Edit /` in the tests, which is the tests'
  problem: those queries were written when the note's own Edit was the only one, and they name
  it exactly now.

- The notes area is a tree of panes, held in `src/notesLayout.ts` — a pure module with no React in it, so the arrangement can be reasoned about and tested without rendering. Splits nest to any depth, and a split inserted along an axis its parent already runs on joins that parent as a sibling rather than nesting, which is what keeps three panes in a row one level deep instead of three. Each pane scrolls on its own so a long note does not drag the note beside it along. A note may be open in several panes but at most once in each, so a tab is identified by the pane **and** the note — `tabId` — while the note's own key still identifies its text. Reading one note beside another part of itself is what a split is for; two tabs in one strip showing the same note would be two ways to the same place. Everything numbering or addressing what is on screen keys off the tab: the element ids in `src/stageNoteIds.ts`, the find's `perTab` and its `data-match-id` ordinals. Everything about a note's content keys off the note: `drafts`, `editing`, `captureOpen`, the captures. That is why typing into one copy shows in the other, and why each copy still has ids of its own.
- The focused pane is the one the outline, breadcrumbs, status bar, and find act on, and it is the only one whose editor may take the caret. Clicking or focusing anywhere in a pane focuses it.
- The slot a drag is aimed at tints the tab as well as the slot. An open tab paints its own opaque `--surface`, which sits over the slot behind it, so marking the slot alone showed the drop everywhere except on the tab a pane was showing — and never at all in a pane holding one tab, since that tab is always the open one. The rule answering it carries the same specificity, so it has to stay below `.panel__tab--open` in the file; a `styles.test.ts` assertion pins that order. The active tab keeps its underline through the tint, so which pane is focused is still legible mid-drag.
- The strip scrolls, so the pane brings the tab it is showing into view whenever that changes: a tab opened onto the end of a full strip lands past its edge, leaving the note on screen and the tab that names it off it. `nearest` on both axes, so a tab already in view is left alone and nothing but the strip moves. jsdom cannot tell a tab off the end from one in view — it lays nothing out and leaves `scrollIntoView` undefined — so the jsdom test asserts that the panel asked for the tab it just opened, and the browser suite measures whether it ended up inside the strip.
- Every pane carries its own tablist, named for its position, and shows exactly one tabpanel — so no tablist is `aria-multiselectable`. Tabs belong to panes rather than to the panel, which is what gives a tab somewhere to be dragged out of and somewhere to land. Each pane is labelled by its own heading rather than by its tab: a tab also carries the current-stage badge and the match count, and a name that changes as you type into the find bar is not a name.
- A note is named `{Company} · {Stage}` everywhere the reader can see it — the pane heading, the tab, and every control inside the pane. Always, even with one application open: a name that grows a company prefix the moment a second one arrives is not a stable name, and two applications at the same stage is the ordinary case the panel now exists for. `src/stageNoteIds.ts` keys its ids on the pair for the same reason.
- The captured lines and the box that adds to them are docked together at the bottom of a pane, pinned while the note above them scrolls: what you were told is the part of a stage still being added to, so it does not scroll away. The log is capped at `--capture-log` and scrolls itself, held at the newest line, so a long conversation cannot push the note above it off screen. Ctrl+K reaches the focused pane's box. Enter must `preventDefault`: the panel is one form around every stage, so it would otherwise save the lot and close mid-conversation. The focused pane is found through a `data-capture-focus` attribute rather than a pane index, so the document-level shortcut is not rebound every time focus moves between panes.
- The dock's edge is a real `separator` with arrow keys, the same contract as the handles between panes, and one height is shared by every pane: dragging the log open for an interview is the reader sizing their workspace, not a property of a note, so it does not reset as tabs change. It travels with the arrangement, clamped between `MIN_CAPTURE_LOG` and `MAX_CAPTURE_LOG`. The floor stops the drag rather than closing the dock — the toggle above it is the way to put the log away, and one control per outcome. `--capture-max` caps the whole dock against the note above it, so a drag to the top of the range cannot leave the note a line high; the value the handle reports is what was asked for, and a short pane may show less of it. The log hugs its content, so raising the height shows more only when there is more to show.
- The dock shows in every mode, including while the note is in the Markdown editor or out with an external session. Captures are their own field, so there is no shared text for a second caret to race — this is the point of the split, and reverting it would put the choice back.
- A pane renders two notes, so the find numbers them the way the eye runs down them: the written note first, then the captures, with `written` in `findMatches` recording where the second starts. A stage in the Markdown editor sits its written note out of the find, because a textarea has no highlights to step onto, but its captures are on screen the whole time and stay in the list. The log passes `foldAll={false}`: a permanent fold-all control costs a row that a pinned strip wants for the note itself, and every day in it still folds on its own.
- The outline collapses with Ctrl+B when the notes want the full width. That is the reader asking for it — do not collapse it, or any other content, on the app's own initiative.
- The sidebar is one panel holding both things a reader navigates with, stacked: **Outline** is where they are in the note in front of them, **All prep notes** is every note behind it. Stacked rather than switched between, because choosing which of the two you want is a question the panel can answer by showing both — and one control is one fewer thing to learn than two. Each half folds from its own heading, and the two share the column on a handle like the panes do: the heading is the control here, which works where a rail's argument did not, because what goes is the list under it and not the row that names it. The fold is session state like the capture dock's; the height travels with the arrangement like every other measurement, and is a **cap** rather than a height for the reason the dock's is — a note with two headings should not reserve room for twenty, and dead space is what this column can least afford. At the narrow breakpoint the sidebar is a strip above the notes.
- The control that opens and closes the whole sidebar is at the **left** end of the title bar, over the column it acts on, rather than filed with Split and Find on the right where it worked at a distance on the far side of the panel. A rail kept permanently to hold one button cost forty pixels of every note for the life of the panel, which is more than the button was worth; the argument that had put it in a rail — a control inside the thing it hides has nowhere to be once hidden — is answered by moving the control out rather than by keeping a column to stand it in. Closed, the sidebar leaves its own edge and nothing else, one handle wide, which is also how it is pulled back out.
- The picker has one control, **Open** in the title bar, rather than a `+` at the end of every strip. It answers what the notes tree cannot — a stage nothing is written for yet — and one control says that once instead of once per pane.
- The title bar's controls are icons, each naming itself on hover and to a screen reader, and unboxed until the pointer is on them — **Open** excepted, which keeps its word and its key on its face. It is the way to a note that is not on screen yet, which is when a reader can least guess at an icon, and it is the only visible place `Ctrl`/`Cmd+P` is written down. Its accessible name is the word alone: the binding is `aria-keyshortcuts`' to announce, and "Open ⌘P" is not a name anyone would say out loud to ask for a button. Four labelled buttons spent more of the bar on saying what they are than on the note it belongs to, and five outlined ones are five frames inside a bar that already has one; they are reached rarely enough that carrying their names and their boxes all the time was the wrong trade. `aria-pressed` is the accent rather than a heavier frame, because it is a state of the thing the button controls — the sidebar is open, the panel is split — not of the button.
- The tree is `src/notesTree.ts`, grouped by the stage a note prepares for rather than by company: that is the question a reader browses with — what does my Interview 2 prep look like across everything — where the tabs and the picker already answer the other one. Stages come out in `STATE_CONFIG` order, walked rather than sorted, so it reads down the pipeline like every other list of stages. A stage with nothing written **and** nothing captured is left out, the tree being a list of places to go back to; one holding only what you were told stays, and says so. Its search filters the tree in place rather than replacing it with results, because the grouping is most of what tells two notes apart, and it matches company and role as well as the words, since a reader typing "Halcyon" means the company. A matching note lists the words around each hit beneath it, up to `MATCHES_SHOWN` with a count of the rest: a search that said only which notes matched left the reader opening each one to find out why. Snippets are flattened to prose — the one place in the app that wants Markdown thrown away rather than parsed — and a row found by its company rather than by anything written in it lists none, which is the honest answer. The words that matched are marked in the snippet with `splitMatches` and `.markdown__match`, the same pair the notes themselves use.
- Picking a hit opens the note and hands the words to the panel's own find rather than highlighting them a second way: the highlight, the fold opened to show a match, the count and the step to the next all live there already, and a second way of showing the same thing is a second thing to keep right. It lands on that note's first match, not the snippet's own position — the tree counts hits in the note read as prose and the find counts them in the note as written, and the two need not agree. The cursor is worked out against the arrangement being applied rather than the one on screen, `findMatches` taking the tab list as an argument for that reason: a note being opened is not among the open tabs until the render after, and its matches would otherwise be numbered from a panel it is not yet in. Every list in the tree carries `min-width: 0`: a snippet is one long line, and a grid item refuses to shrink below its content, so without it the lists size to the longest snippet and run past the sidebar rather than ending in the ellipsis the text asks for. Names carry themselves as a `title`, the column being too narrow to show a company and a role at once.
- The sidebar's own width is draggable, from a `separator` with arrow keys like the handles between panes, and travels with the arrangement. `MIN_SIDEBAR` is both the narrowest it goes and the point past which it closes instead: a column too thin to read its own rows is not a narrower sidebar, it is a sidebar in the way. The floor is what the sidebar's own contents can be squeezed into rather than a guess — the shared `.search-field` holds a `9rem` floor that is right in the context bar and wider than the whole sidebar here, so this is the one place it gives it up, and the `input` inside needs `width: 100%` of its own because the rule sizing the context bar's copy is scoped to that bar. A stage heading truncates while the count beside it holds its width. One rule rather than a floor with a separate collapse point below it — with both, the clamp held the width above the threshold and the collapse could never be reached. The handle is drawn **after** the panel, the body being a grid whose columns are filled in the order its children appear; put before it, the panel took the handle's track and the width went to a one-pixel column. It is drawn whether the sidebar is open or shut, because it is how the sidebar is pulled back out as well as pushed in — a width is something to drag *to*, not only away from — and what comes back is the panel that went rather than a default. `.panel__body--rail` declares two tracks for that reason — the edge and the notes — since a grid given fewer tracks than it has children wraps the rest onto a row of their own, which is where the edge went when the count was wrong. The pointer drag measures from the body's own left edge instead of accumulating deltas, a closed sidebar having no width to add to; the arrow keys step from the current width, and closed, the only step that means anything is the one that opens it.
- A row in the tree is a drag source for the same drag the tabs use, landing in the same places: among a pane's tabs, or on a pane's edge to split one open there. That is the point of dragging one — a click opens a note into the pane being read, and a drag is how you say which pane instead. `placeTab` is one function for both cases because they are one operation from the reader's side: a note dragged onto a strip lands there, and whether it came from another pane or from the tree is the panel's business rather than theirs. The key a drag carries is resolved through `parseNoteRefKey` when no open tab holds it, since a note in the tree has no tab to read the ref off. A row asks `wasDragged()` before acting on the click a browser sends after a pointer sequence: dropping a note on one pane is not also a request to open it in another. The keyboard equivalent is the click plus the tab-move shortcuts, which keeps the rule that every arrangement a drag can reach has one.
- The panel is a container (`.panel-view` carries `container-type: inline-size`), and every rule that stacks or narrows it is a `@container panel` query rather than a `@media` one. The window was the right measurement only while the panel was a full-viewport modal; in a view the surface takes a gutter each side, and a panel can be narrowed by anything. The title bar, the stage header and the status bar all wrap, because the panel clips its own overflow: a row that cannot wrap loses its last control rather than scrolling to it. `.panel__notes` needs `min-width: 0` for the same reason — it is a grid item in an `auto` track, so without a floor of zero the track takes its min-content (around a thousand pixels of tab strip, note header and capture box) whatever the panel was given, and everything past the panel's edge is clipped: the breadcrumbs, the tab strip's end, the status bar and the right of every note. `1rem` is 14px here, not 16 — `:root` sets `font-size: var(--t4)` — so a rem-based cap is smaller than the px token it is meant to match.
- What is open is the panel's own arrangement, not a reading of which notes exist. An external editor emptying a note leaves its tab where it was, showing the note as empty: clearing a note is not a reason to rearrange the panes around whoever cleared it. Closing the last tab in a pane prunes the pane, and a split left holding one child collapses — `prune` does both, so no render shows an empty pane or a split that splits nothing. Closing the last tab anywhere leaves the view open on its empty state and forgets the stored arrangement; the panel itself never renders with nothing open, which is the invariant everything it derives from the note on show depends on.
- The prep notes surface is flush to the sides and the top of the window — a step of space at the foot, where the status bar and the dock above it would otherwise sit on the edge itself — and carries no border and no rounded corners, where the four views of the collection are cards laid on the page with a gutter around them. That shape belonged to the heading that named the view; with the heading gone the card drew itself around a workspace filling the screen, and every pixel of the inset was charged to the notes. The topbar's own bottom border is the line between the two.
- The panel pins its title bar, tab bar, breadcrumbs, outline sidebar, and status bar, and scrolls only the notes column, so a note of any length leaves the stage list and the write state reachable. That only holds while the page behind it does not scroll either, so the shell is pinned to the viewport for this view — `.app-shell:has(.view-surface--panel)` takes `100dvh` and drops its own `min-height`, because a minimum outranks a maximum and `100vh` would win over the cap on exactly the viewports the cap is for. The panel's height still comes from the flex column above it rather than from a measurement of the header. A note is what the panel is for: give the notes column the width and leave the chrome dense. Dense is measured, not asserted — with several panes open the chrome is charged per pane, so one step of padding costs as many times as there are panes. The pane, the note body and the note header each sit a step down the spacing scale from a form's, and the tab strip takes `--control` rather than `--control-form`, including the `+` that sets the strip's height.
- The note header holds the date and the controls that act on the note and the pane, and nothing that names it: the name is `sr-only` — the tab directly above says it in full, in every pane and at every width — and the stage moved to the title bar. It had been the header's first visible element, which made a control stand in for a heading, and stood it flush against the formatting toolbar with which it shares no scope: the select swaps which note is in the pane, where the buttons beside it change characters. The parts that remain want some seven hundred pixels between them, so the header wraps rather than giving each a row of its own — the controls carry `flex: none` so they wrap as one piece, and `.stage-note__meta` takes the slack so what follows it ends the row. The date shows without the word "Updated", which is left to a screen reader: a bare date in a note header reads as when it was last written, and the word costs the row that the date and the controls otherwise share.
- The title bar's subject — the focused note's company and role — carries the control that opens that application's editor, immediately to its right. It is beside the name it acts on for the reason the sidebar toggle is over the column it opens: the bar already says which application is being read, so the record behind that name is one step from it rather than a trip back to the board to find the card again. One control for the panel rather than one per pane header — it follows the focused pane the way the breadcrumbs, the outline, the status bar and the find do, and pane chrome is charged once for every pane on screen. It is named **Open the application for {company — role}** rather than "Edit": the card and the table row reach that same dialog with Open, and a second control beginning "Edit" beside a note's own Edit/Read is two things to tell apart at a glance. It renders only when the focused tab names an application the document still holds, which is also when the title beside it has anything to say. The dialog opens **over** the panel rather than instead of it: the arrangement, the drafts and the captures are the panel's own state, so unmounting it to change a company name would throw the lot away. Nothing it writes touches `stage_notes`, which is absent from `ApplicationEdits`, so there is no second writer for a draft to race. The stage select sits on the other side of it, because the stage continues the name: which application, then which of its stages. It acts on the focused pane like the breadcrumbs, the outline, the status bar and the find do — a pane that is not focused still says which stage it holds on its own tab, badge and all, so what a split gives up is the switch and not the reading, and clicking a pane is what focuses it. It carries no current-stage tint: that tab badge says the same thing one row above, and the pill said it twice. `field-sizing: content` is what sizes the pill to the stage it is showing rather than to its widest option, and nothing caps it below that: a stage is a name, and one cut to "Recruiter messa…" is the single thing the pill exists to say. It was held to `9rem` to stop the longest label widening the bar, which bought that width by spending the value. The name is what gives instead, under a shrink factor lopsided enough that the stage is reached only once there is no name left to spend — and the name is written out in full on the tab below, which is the same trade the note header makes for the same reason. `max-width: 100%` is a floor of last resort rather than a cap: a panel too narrow for the whole label ends in an ellipsis instead of pushing it past the edge the panel clips at. `.panel__subject-group` is what keeps the three together — the name gives up the free space to the group and ellipses, so a long company name cannot push the control to the far end of the bar among the panel's own chrome.
- A stage being written fills its pane's height, so the editor offers the room the reader gets rather than a box the size of a short note. The stretch is scoped with `:has()` to the card holding an editor: a short note being read still sizes to itself instead of stretching its card down an empty pane.
- Only the active tab's note is mounted, but every open note's draft stays in `drafts`, keyed by `noteRefKey`. Nothing about the panel's own state—which tab is showing, what is folded, what has been found, how the panes are sized—may reach a saved note.
- The panel has no Save. Drafts write themselves `AUTOSAVE_MS` after the typing stops, and again as the panel unmounts so the last keystrokes are not lost — prep notes are typed mid-interview, where a closed tab is likelier than a deliberate Save. Only the notes that changed are sent, measured against `stored` rather than against the saved note, because `applyStageNotes` trims a body and a draft ending in a space would otherwise be re-sent forever. Drafts go out **grouped by application**: `applyStageNotes` allows one draft per state in a call, so a panel holding two companies' notes cannot send one flat list. `App.tsx` folds the batches into a single `commit`, so the lot is still one write.
- Writes run one at a time behind `savingRef`: each one PUTs the whole document, so an overlapping write would be built on a document the first has already replaced. Typing during a write stays pending and is picked up by the loop before it lets go. A failed write leaves its drafts pending and says so in the status bar; the panel never claims to have stored what it has not.
- The debounce hangs off `drafts` and nothing else. Its identity changes only when a draft is edited, and every write re-renders the parent — anything else in the dependencies restarts the wait on the panel's own writes and it never fires.
- A file coming back from an external editor is marked stored as it commits, so the poll's own write does not come back round as an autosave of itself.
- A tab's close control means off screen, not deleted: the note stays in the document and the stage is listed again next time the panel opens on that application. **Every tab closes, the current stage's included** — with notes from several applications in one panel there is no single stage it must always keep, and an undismissable tab per application would only pile up.
- A tab is dragged with **pointer events**, not HTML5 drag-and-drop, and that choice carries two things at once: a finger works, and a test can drive it. HTML5 drag has no touch story — `dragstart` is a mouse event — so the panel used to be rearrangeable with a trackpad and not with a thumb; and no browser automation can start a native drag session, so it could not be tested in a browser either. One pointer path covers mouse, touch and pen. `src/useTabDrag.ts` holds it. A tab can be dragged to reorder it or to move it into another pane, and `Ctrl/Cmd+Shift+←/→` and `Ctrl/Cmd+Shift+,/.` do the same from the keyboard. Both routes call one `dropTab`, over `moveTab` in `notesLayout`, so a drag cannot reach an arrangement the arrows cannot — the requirement the Kanban's `Move` select answers for dragging a card. The tablists carry an `aria-describedby` sentence naming both, because a drag is otherwise undiscoverable without a pointer and its keyboard equivalent undiscoverable at all.
- Opening a note is always **into the pane being read**, whatever another pane is showing: a card, a table row, the tree, the picker and `Ctrl+P` all end in `openInGroup` on the focused pane, which shows the tab when that pane already has it and adds one when it does not. Reaching for a note is a request to have it here, not to be sent to wherever a copy of it happens to be — the panel never moves your attention to another pane because it found the note there first. Only the pane's own tabs are consulted, so "already open" always means already open *here*, and the picker's Open badge is computed against the pane the picker belongs to for the same reason.
- A drag says something different, and says which by what it carries. A tab hands over its `tabId`, so dropping it **moves** that copy out of that pane — `moveTab`, which takes the pane to take it from rather than looking for whichever holds it. A row in the notes tree hands over a note key, which names no pane, so dropping it **places** a copy where it lands and leaves every other copy alone — `placeTab`. `splitWith` takes the pane to detach from for the same reason, and Split passes its own pane, since showing two notes at once is not a request for two of one.
- Split adds a pane, every time, and asks where it goes: right, left, below or above, from a menu on the control. It was a toggle — a second press gathered every pane back into one — which put "back to a single pane" under the control a reader presses when they want a third, exactly when they have two. Coming back is its own item at the foot of that menu, and gathering folds copies into one tab since a strip holds a note once. The four are drawn where they point — Above over Left and Right, Below under them, the pane being split drawn in the middle so the four read as its sides — decoration, `aria-hidden`, since each button already says where it opens — because a list reading "Right, Left, Below, Above" asks the reader to translate a word into a side of the screen. Source order follows the drawing, top to bottom, so Tab walks the cross rather than jumping around it. There is no right default direction at three panes, so none is assumed: side by side is for reading two notes against each other, stacked is for following one into another. `Ctrl/Cmd+\` opens the menu and lands focus in it, where an arrow says which way — the pair rather than four chords, because every arrow with a modifier is already spoken for: Shift sends the tab being read to an edge, Alt walks it along the strip. Each direction carries its arrow on its own button, the rule the title bar keeps for every shortcut here, and the three columns are one width — sized to their contents, "Left" and "Right" came out narrower than the pane between them and the map read as a ragged list. The pane opens **empty**, and focus goes to it: what was asked for is room, and which note goes in it is the next thing the reader says — from the picker, from the tree, or by dragging a tab across. A pane arriving with a note chosen for it was a guess, and half the time the guess had to be undone first.
- An empty pane is a place, not a state to be tidied away. `prune` no longer drops empty groups — it only collapses splits — because a pane opened empty has to survive every operation happening elsewhere in the tree. Removing a pane is explicit now, through `withoutGroup`, and the operations that empty one call it: closing the last tab in a pane, dragging the last tab out, closing the pane. So both rules hold at once — Split makes an empty pane, and a pane that *loses* its last note still goes. A panel with no note anywhere is still no panel: `closeTab` returns null when nothing is open, and `restoreArrangement` drops an arrangement holding only empty panes. Reconciliation tells the two apart by what was stored: a group stored with tabs and left with none lost them to a deleted application and goes; a group stored empty comes back empty.
- The chrome follows the nearest pane holding a note, not necessarily the focused one. The outline, the breadcrumbs and the status bar are about a note, and the focused pane can be empty; focus itself stays put, which is what makes the next note open where the room was made.
- Dragging a tab onto the edge of any pane splits a new one open there, and `Ctrl+Shift+←/→/↑/↓` does the same from the keyboard — moving into the pane already on that side, or splitting when there is none. One binding for both cases because they are one intent: put this note over there. Which pane is on a given side comes from `neighbourGroup`, which walks up to the nearest ancestor split running on that axis rather than measuring the screen; layout does not exist to be measured until after a render, and the tree is the thing that actually decides.
- The drop zones are real elements per edge, raised only while a drag is running, rather than a reading of the pointer against the pane's box. The browser does the hit-testing it is already good at, each zone can be highlighted on its own, and nothing has to measure a layout jsdom does not have. They are `aria-hidden`: there is nothing there to operate without a pointer, and the arrows do the same job for anyone who has not got one.
- The divider between two panes is a real `separator` with `aria-valuenow` and arrow keys, the same contract the table's column handles keep, for the same reason: a drag is no way at all without a pointer. Both routes go through one `onResize` over `resizeSplit`, which clamps at `MIN_PANE_FRACTION` — a drag past the limit stops there rather than collapsing a pane, because nothing is easier to lose than a pane you cannot see. jsdom has no layout, so the keyboard path is what the tests drive and the pointer path cannot be asserted; that is a reason to keep both behind one call, not a reason to test neither.
- Pane widths are display state like the folds and the find: they last while the panel is open and never reach a saved note.
- Three keyboards decide what a binding here may be, and only the last is ours. **The browser takes some combinations before the page sees them**: `Ctrl`/`Cmd+W` closes its own tab — the one mechanism that could capture it is Keyboard Lock, which only captures in fullscreen, so do not re-litigate this with a `preventDefault`, which is ignored for that key and which no test can show, since synthesized events never reach the browser's own shortcut handling — and on macOS `⌘⌥←/→` walks between browser tabs, which is how the reorder binding came to do nothing at all. **A text box takes others while it holds the caret**: `⌘⇧←` selects to the start of a line, so the arrows that move a tab are answered only when nothing is being typed into, which `isTyping` decides. What is left is ours: closing is `Ctrl`/`Cmd+Shift+X`, reordering is `Ctrl`/`Cmd+Shift+,/.`.
- A modifier that rewrites the character is a trap either way round. Option does it to letters — ⌘⌥W arrives as `∑` on a US layout — and Shift does it to punctuation: `⌘⇧,` arrives as `<`. So the punctuation binding matches `event.code` **or** the character, since `code` names a key cap and a layout that puts a comma elsewhere reports that cap; letters with Shift need no such care, `X` being `x` upper-cased. Neither user-event nor a browser driver reproduces the rewriting — both set `key` to the plain character — so a test driving them passes while the binding does nothing on the machine it is for; the regression tests dispatch what the machine actually sends. The constants that name bindings on the tabs look them up by key **and** modifier: a lookup by modifier alone handed one binding another's label the moment a second shared it.
- The two arrow bindings are bound apart from the five letter ones. Folding them together would mean testing for the absence of Shift and Alt on every letter, which is how `Ctrl+Shift+F` quietly stops opening the find bar.
- Focus follows a tab selected with the arrow keys. Leave it behind and the next arrow key is read by the tab that no longer matters, stepping from the wrong place.
- The sidebar outlines the active note's headings, and the breadcrumbs name the last heading scrolled past. Both are derived from the section tree, but which heading is current reads layout rather than the tree, because a folded heading is not on screen to be inside. `NOTE_HEADER_PX` in the panel has to track `--note-header` in the stylesheet.
- The outline is a nested list, one per level, so the hierarchy is in the markup rather than only in the indentation. `outlineTree` nests by section structure, not by comparing heading levels, so a note that opens at `###` and later uses `##` still outlines the way it reads.
- Three things carry the hierarchy, and all three are needed: an indent guide per level, a type ramp that quietens deeper rows, and the path down to the current section marked the whole way. The row modifiers carry `[data-depth]` so they outrank that ramp at any depth — drop it and the mark disappears exactly where the outline is deepest.
- A tab says what tells it apart from every other tab on screen, worked out in `src/notesTabLabel.ts` over the whole panel rather than one strip at a time: the company only when more than one is open anywhere in it, the role only when one of those companies has two roles open, the stage always. A panel holding one application's stages is then short tabs rather than copies of the same sentence — and two panes holding one company each still name both, which asking pane by pane would not, since neither pane would find a second company in itself. The whole name is not lost — it is the tab's `title` and, through a visually hidden span, its accessible name, so a query by full name still finds it and a screen reader still hears it; `textContent` therefore holds both, and a test reading the strip should read `.panel__tab-label`. A tab is also capped at `18rem`: a role can legitimately read "Senior Software Engineer - Product & Features (Java)" and a tab cannot.
- `.panel__notes .stage-note__editor` declares its rows rather than counting them, so moving a control out of the editor leaves an empty track behind and the field drops into a row sized to its content — a small box with its own scrollbar at the top of an empty pane. It holds one row now, the field. Change the template whenever what the editor renders changes; the browser suite measures the field against the pane for exactly this.
- The note's first row carries what is being done to it: the stage it is, the day it was written, folding, formatting, and the way out. Folding and formatting are handed up by whichever mode is showing — `MarkdownNotes` and `StageNoteEditor` each report a fold control through `onFoldControls`, and the editor leaves its formatter on a `formatRef` — so the pane draws them and neither costs a row of its own. Both children keep drawing their own where nobody takes them, which is how the Compare view still gets them. What is reported upward must be stable: a callback rebuilt every render becomes a new value in the parent's state on every render, and that is a loop. Keep the moving parts in a ref written from an effect, never during render, which the lint rules also require.
- The note header does not print the note's name. Its tab is directly above it, in the same pane, always scrolled into view. The `h3` stays `sr-only` for the accessible name.
- The close over a tab is `--control` wide whatever its icon measures, so a tab reserves that much padding at its end; and hidden it must take no pointer events, since `opacity: 0` alone still answers a press. Both only started mattering when tabs got short: the control had been landing on the middle of "Offer", where a press meant to read a note closed it — silently on a touch screen, which has no hover to reveal what it is about to hit.
- The sidebar's two halves divide the column between them rather than the outline taking a height of its own. A share is what the handle stores — half each to begin with — so it means the same in a tall window and a short one, and so folding one half hands the whole column to the other instead of leaving the space it gave up to nobody. The column does not scroll; each half scrolls what it was given, since a column that scrolled as a whole would make the division meaningless. An arrangement stored under the old `outlineHeight` is ignored rather than read as a share: a stored 180 would clamp to the ceiling and hand the outline everything.
- The outline's rows are one line of text and carry no control height, so they set at the same rhythm as the tree under them — one sidebar, not two lists of different kinds. `--control` goes back on them in the coarse-pointer block at the foot of the stylesheet, which is where density gives way to a finger. Note that the note body folds its headings with buttons named after the same headings: a test reaching for an outline row by name finds one of those first, so scope it to the `Outline` list.
- Grids in this sidebar say `align-content: start`. A grid hands leftover height to its auto rows, which is almost never what a list wants: both halves folded put one heading at each end of an empty column rather than one under the other, and a tree with room to spare dealt the slack out between its stages until it read as fragments rather than a list. It shows up as slack inside a group, under its last row, not as a wider gap between groups — measure a group against what is in it. Tracks sized in `fr` consume the leftover themselves, so this only ever speaks for the cases that are not.
- A handle has to be drawn. The one between the halves is painted at rest and bleeds through the column's padding to both edges, so it reads as the line dividing them as well as the thing that moves it; a handle that appears only on hover is one nobody finds. The same is not yet true of the sidebar's own outer edge, which is still transparent until reached for.
- The outline stays a tree at every width. The narrow container query caps the sidebar's height and lets it scroll; flattening it into a strip of chips would trade the hierarchy for the space it saves.
- The outline repeats heading text, so two buttons in the panel can hold the same words. Outline entries carry a `Go to …` label to keep them apart, and a test looking for note content scopes itself to the `tabpanel`.
- Quick open (Ctrl+P) reaches all 19 stages, not only the ones on screen, and is the only way to start notes for a stage the application has not reached. It takes over the browser's print shortcut while the panel is open, as Ctrl+F takes over its find. Ctrl+\ splits and Ctrl+B collapses the outline.
- `src/shortcuts.ts` describes those five bindings once — key, wording, platform modifier label — and the listener, the title bar hints, and the shortcuts list all read from it, in the order and the words the README's **Keyboard shortcuts** section uses. A binding the panel answers but nothing on screen names is a binding only the README has. `modifierLabelFor` is pure in its platform, like `resolveEditorCommand`, so `⌘` on macOS and `Ctrl` elsewhere is asserted on rather than hardcoded; `aria-keyshortcuts` lists both modifiers because the panel answers either on any platform.
- The shortcuts list is a disclosure in the title bar, the same shape as the topbar's More actions. Its Escape is a React handler on the container rather than a document listener, so one key press closes one thing. Any further overlay in this panel owes Escape the same treatment — the find bar and the stage picker each pay it from their own input. Escape has no panel-level meaning: with the find bar and the picker closed it does nothing, because a view is not dismissable and the tab strip is how a reader leaves.
- Finding text inside notes is the panel's own, not the browser's: a folded row is unmounted, so `Ctrl`/`Cmd+F` is taken over and answered from the AST. `searchNote` returns the match count, the fold keys a match sits behind, and each text container's first ordinal in one pass; the renderer numbers its highlights from those ordinals rather than from render order, so a re-render cannot renumber the matches under the find bar.
- A fold opened to show a match closes again when the find closes. Revealing is derived state layered over the reader's own folding, never a write to it.
- An overlay in this panel owes a reader a way out that can be seen. Escape is the shortcut, not the answer: nothing on screen says it is there, and a palette floating over the panel says nothing about itself. Both the find bar and the stage picker carry a close button in their own row, and the picker also closes on a press anywhere outside it — subscribed on `pointerdown` from the tick it mounts, which is safe because it opens on a click and a click's own press is over by then. Do not wait a frame to subscribe: a frame is not guaranteed to arrive, and the listener is missing until it does.
- Escape closes the find bar and nothing further; `FindWidget` stops the key rather than letting it travel, and any other overlay added inside the panel owes the same.
- A stage open in the Markdown editor is searched as the source it is, and its matches are counted with the rest so one list runs through the panel. `matchOffsets` finds those ranges with the same matcher `splitMatches` uses, so source and rendered notes agree on what counts.
- A textarea carries no highlight, and an unfocused one paints no selection either, so `stage-note__marks` mirrors the text behind the box: transparent apart from the matches, which is what makes them visible while the caret stays in the find bar. Every property that decides where a character lands — font, size, line height, wrapping, padding, border width — is stated on both, because the mirror drifts off the words the moment one of them differs. Wrapping in particular is stated rather than left to the browser's textarea defaults.
- The mirror sits outside the `label`, never within it. A label names its control by its content, so a mirror inside would read the whole note out as the box's name.
- Stepping never takes focus out of the find bar, including from the step buttons, which put it back. Enter therefore goes on stepping instead of repeating the click. The step still sets the selection, unfocused and invisible, so clicking into the box afterwards lands on the hit.
- Revealing happens on a step, never on a keystroke. The cursor moves on every character typed into the find box, and following it would scroll the note about under someone still deciding what to search for. It is also deferred a frame, because the step may have just moved that stage into a pane.
- Scrolling the box to a match reads the mark's `offsetTop` off the mirror. Measuring where a character offset sits inside a textarea is otherwise guesswork.
- Captured lines open for correcting still sit out of the find: each is in a box of its own, and there is no one place to send a caret that stands for all of them.
- The find searches every stage, including tabs that are not rendered, and stepping onto a match in another stage switches to it. That switch happens in the step handler, from the cursor's new position, not in an effect watching it.
- A stage that already has notes opens as a rendered outline; an empty stage opens in the editor. Read and edit mode, and which points are folded, are display state and must not be persisted.
- `src/markdown/parseMarkdown.ts` supports headings, nested ordered and unordered lists, paragraphs with hard line breaks, block quotes, fenced code, bold, italic, inline code, escapes, and links. It is deliberately a subset, not CommonMark. Links render only for `http`, `https`, and `mailto` targets; anything else falls back to plain text. Bare URLs, bare email addresses, and `<…>` targets autolink, because notes are pasted into more often than they are marked up; autolinking is off while a written link's label is parsed, since a link may not nest inside another. A `#fragment` destination is kept as written and resolved against the note's own headings, whose slugs `sectionSlugs` builds the way a generated contents list writes them; following one jumps within the panel and never navigates. Extend the parser and its tests together.
- The editor's hint is the only place a writer learns what that subset is, so it lists everything the parser takes. Quotes and fenced code were supported and foldable for a long time while the hint named neither, which is the same as not supporting them. Extend the hint with the parser.
- A quote takes the line straight after it, so `> Question` followed by an unmarked `Answer` reads as one quoted paragraph. That lazy continuation is deliberate — it is what makes a quote survive a wrapped line — but it means a blank line is the only way to end one, and the hint says so.
- A list item holds `children: BlockNode[]`, so anything indented under a point—nested lists, paragraphs, quotes, code—belongs to that point. A line that merely wraps the point keeps flowing into its text; content after a blank line, or starting a block of its own, becomes a child. That distinction is what decides whether a point folds.
- Everything with hierarchy folds: a heading folds through to the next heading of equal or higher level, a list item folds when it has children, and quotes and code blocks fold behind a summary. Keep fold controls as real buttons carrying `aria-expanded`.
- `FoldRow` renders one pattern for every fold: a chevron `button` that owns the accessible name and keyboard focus, plus adjacent text that toggles on click. Do not wrap the text in the button—note text contains links, which may not nest inside a button, and a button would make the note hard to select and copy. The text handler ignores clicks that land on a link or that end a non-collapsed selection; keep both guards.
- Fold keys come from the `blockKey`/`itemKey` helpers in `src/markdown/sections.ts`, and the renderer, the Collapse all collector, and the note search all walk the tree with them. A key that means one thing to one of them and something else to another folds or reveals the wrong rows. Adding a foldable block means updating `collectBlockKeys` and `searchNote` alongside the renderer, or Collapse all silently misses it and a match behind the new fold never opens. The integration test that collapses every level exists to catch exactly that drift.
- `searchNote` walks containers in the order the renderer visits them—a section's heading, then its blocks, then its subsections; a list item's own line, then its children. Reordering one without the other misnumbers every highlight after the change.
- A Kanban card shows the soonest invite that is still ahead, skipping cancelled ones and using the same
  browser-local day boundary as overdue grouping, so an invite earlier today still counts.
- A Kanban card also carries its preference, which is the one thing on the board that cannot be derived
  from anything else the card shows. It renders the full `describePreference` text, not a bare number: a
  score alone would read as more certain than it is, and the weakest judgement is the point of showing it
  at all. An unrated card shows no preference line rather than a dash, because the board is scanned rather
  than read in columns.
- The table bands rows into `due`, `undated`, `outstanding` and `closed`, defined in `src/views/urgencyBands.ts`.
- Every band heading must state its own membership rule in plain terms ("Live, nothing dated", not "Later"). If a rule changes, the heading changes with it. The `due` heading states its order as well, because that band reads by date rather than by score.
- Band placement is decided by the nearest of the soonest upcoming invite, `deadline_at`, and `next_action_at`, not by which pressure wins the score. Urgency pressure decays to zero past its horizon, so banding by the winning term would file an action dated ten days out as unplanned. A live application with no date at all is `undated`, whether or not it has a named task: the band is about dates, and the Next action column already says whether there is a task.
- A row describes its own date via `describeDue` when it has one, so a heading and a row can never disagree about the same date. `describeDue` in `src/views/urgency.ts` is the only place date phrasing is built.
- The bands are not actions-only: an application with a deadline and no next action still bands as `due`. Conversely a task left on a rejected, accepted, or no-openings application must stay visible under `outstanding` rather than being lost among the finished rows, because the ranking omits finished applications entirely.
- The `due` band sorts chronologically by the driving date, because a dated band is read as a schedule and its heading promises it. Every other band keeps ranked order.
- The within-band chain is `compareBanded`: the band, then the band's own rule, then the urgency score, then preference descending with unrated last, then company so the comparison is total. Preference sits near the end deliberately: it can only reorder rows the ranking would otherwise have settled arbitrarily, so it never overturns a date or a score. Its effect is invisible until enough applications are rated to tie, which is why `preference.test.ts` builds a deliberate tie rather than trusting real data to produce one. `compareBanded` compares scores with the ranking's own `SCORE_EPSILON` so the two cannot disagree about what "tied" means.
- A band heading is a `<th scope="rowgroup">` spanning every column, inside its own `<tbody>`: the heading applies to the rows under it, not to a set of columns. A band holding nothing renders no `<tbody>` at all.
- A deadline surfaces in the table, both in its own column and by banding the row as `due`.
- A table column whose value can be absent returns `null` from `comparableValue`, and the comparator settles presence before it applies the sort direction. A sentinel number cannot do this: whichever end you pick it sorts to the wrong one as soon as the direction flips, which is exactly how the deadline and invite columns used to put undated rows first when sorted descending. Deadline, invites, preference, and compensation all rely on this, and each has a both-directions test.
- Urgency is derived in `src/views/urgency.ts` and must never be persisted: it depends on browser-local "today", and a score without the weights that produced it is meaningless. Keep the weights in that module, not in the tracker document or `indexes`.
- Preference is derived in `src/views/preference.ts` and never persisted, for the same reason as urgency: a score without the weights that produced it is meaningless. `DEFAULT_RATING_WEIGHTS` lives in that module, and there is nowhere to persist a different policy — the document shape is closed and discards any extra top-level key.
- The compensation comparison is derived in `src/views/compensation.ts` and never persisted, for the same reason: which figure counts as *the* figure, and whether a band straddling the target is short or merely undecided, are policy. Only the figures themselves are stored. Unlike preference it is not a score and carries no weights — the numbers are already comparable, so nothing there invents a scale.
- The compared figure is `offered ?? advertised`. `expected` is excluded because a target is not a number anyone quoted you, so an application holding only an expectation has no figure at all and sorts last despite showing one.
- The gap is measured between the nearest ends of the two bands, so it reports only what the bands guarantee: `below` means the figure cannot reach the target, `above` means it clears all of it, and overlapping bands are `within target` with a gap of exactly zero. A midpoint difference would state a policy as a fact.
- The Compensation column sorts by the midpoint of the compared figure and ignores currency, because there is nowhere to persist conversion rates and inventing them would be worse. A tracker mixing currencies must read the column rather than trust its order, which is why every cell states its currency first.
- Compensation is never folded into urgency or preference and never affects band placement, for the same reason ratings are not: urgency already carries a stage factor, so a second factor compounds until a deadline today loses to one next week that happens to pay better. A regression test in `src/views/compensation.test.ts` asserts `urgencyFor`, `rankByUrgency`, and `urgencyBandFor` are unchanged by it.
- Compensation is deliberately absent from `search_text`, the same as ratings and for the same reason: these are numbers, not prose. Indexing them would make a search for `offered` match every application that has one and `150` match any application holding 150 in a band.
- The Compensation column filter is a stage picker (`any`, `advertised`, `expected`, `offered`) plus a min/max range, not a text box, matching `matchesCompensationRange` in `src/views/compensation.ts`. A bound checks overlap against the relevant band, the same policy `compensationGapFor` uses for `within target`, not containment — a 100,000-130,000 posting matches a 120,000-150,000 query. `any` checks every stage; a named stage excludes a row that holds nothing for it, even when another stage would have matched. Either bound may be left blank, which reads as unbounded rather than zero. Unparseable text in a bound is treated as unset rather than as an error, so a half-typed number does not hide every row. Like the sort, it is currency-blind: there is nowhere to persist conversion rates.
- The preference score is `mean(rated) - MAX_UNKNOWN_DISCOUNT * (missingWeight / totalWeight)`, so the bound is `mean - MAX_UNKNOWN_DISCOUNT < score <= mean`. That bound is independent of how many dimensions exist. It does **not** mean a rating difference always wins: a mean gap smaller than the discount can be overturned, and `5,-,-,-` losing to `5,5,4,4` is intended and asserted. Only a gap of the full discount is guaranteed safe.
- The discount uses weight share, not count share, so a dimension weighted zero costs nothing whether it is judged or not, and it is excluded from `lowest` too. Weights are clamped to zero at the low end; a negative weight would push the discount past its bound.
- Nothing judged returns `null`, which sorts last in either direction rather than as the worst score. Unrated is not bad, and a fresh tracker must not read as a wall of rejects.
- `lowest` exists because a mean hides dealbreakers: `5,5,5,1` and `4,4,4,4` both score 4.00. `preferenceFor` reports it without a threshold; `describePreference` holds `DEALBREAKER_SCORE` and decides when to name it.
- `describePreference` is the only place preference phrasing is built, the way `describeDue` is the only place date phrasing is built. The table column and the Kanban card both read it, so two views cannot describe the same ratings differently, and the table's column filter still matches its own rendered text.
- Preference is never multiplied or added into the urgency score and never affects band placement. Urgency already carries a stage factor, so a second factor compounds and a deadline today on a poorly rated application loses to one ten days out that happens to be rated well. Regression tests assert `urgencyFor`, `rankByUrgency` and `urgencyBandFor` are unchanged by ratings. Order within a band and display are the only things preference is allowed to touch.
- Completed actions **are** in `search_text`: they are prose you wrote, and before Done had a field of its own they lived in `notes` and were already matched. Every save rebuilds the indexes unconditionally through `refreshTrackerDatabase`, so the addition takes effect on first save; only a document that is loaded and never saved keeps the older text.
- Correspondence **is** in `search_text`, like completed actions and for the same reason: it is prose, and
  until it had a field of its own it was being typed into prep notes, which are already indexed — leaving
  it out would make filing a recruiter's email properly a search regression. The correspondent's name goes
  in with the text, because a name is what a reader searches by. The channel does not: it holds one of a
  handful of words on most records, so indexing it would make `email` match every application you have ever
  emailed. That is the test `source` passes — one value per application, so it partitions the collection —
  and the one ratings and compensation fail.
- Ratings are deliberately absent from `search_text`. They are numbers, not prose: indexing them would make a search for `work` match every rated application and `4` match anything holding a 4. `indexesAreStale` cannot detect `search_text` content drift either, so existing documents would under-match forever. The Preference column filters its own rendered text instead.
- Only live applications are ranked. `classifyLifecycle` treats every `rejectedStateFor` counterpart as rejected and `accepted`/`no_openings` as closed; both are omitted from the ranking rather than scored low. This is view grouping only and must not restrict moves.
- Stage weight comes from position among the live states, not the raw `STATE_CONFIG` index, because the configured order interleaves live and rejected states.
- The highest single pressure sets both the score and the displayed reason; the others stack only into the headroom above it.
- Horizons encode confidence, not importance. Every dated term peaks at 1 on its own day, and a firmer commitment decays more slowly: an invite over `INVITE_HORIZON_DAYS`, a deadline over `DEADLINE_HORIZON_DAYS`, a next action over `ACTION_HORIZON_DAYS`. So at equal distance an invite outranks a deadline and a deadline outranks a date you set yourself, while an overdue action still outranks an invite that is days away. Staleness is capped below all of them because it is inferred rather than recorded. Ties resolve in the same order: invite, deadline, action, staleness.
- Staleness measures days since the last `state_history` entry, via `daysSinceLastMove` — never `updated_at`. Any edit refreshes `updated_at`, so reading it would let saving an invite or fixing a typo reset the silence the term exists to detect. Idle reads the same `daysSinceLastMove`, so with the Stale view gone no surface measures silence from `updated_at` at all. `applicationAgeInDays` is now only the day-difference helper `daysSinceLastMove` counts with, not a measure of its own.
- Two measures read the same history, and which one a surface uses is deliberate. The urgency term ramps `daysSinceLastMove` from `STALE_GRACE_DAYS` to `STALE_PEAK_DAYS` and answers "how hard should this push". **Idle** thresholds the same measure at `IDLE_THRESHOLD_DAYS` and answers "is this one quiet, yes or no". A surface that wants a yes-or-no about silence uses Idle; do not add a third.
- Only invites still ahead carry pressure, cancelled ones never do, and `upcomingStateEvent` enforces both. A meeting that already happened is history, which is the one place invites and deadlines differ: a passed deadline stays urgent precisely because it slipped.
- Rank comparisons treat scores within `SCORE_EPSILON` as tied so the documented tiebreak (deadline, then action date, then age, then id) decides the order instead of floating-point noise.
- Idle is a second axis over stage, not a twentieth state: `idleStatusFor` returns a day count for a **live** application whose last `state_history` entry is `IDLE_THRESHOLD_DAYS` (30) or more in the past, inclusive, and `null` otherwise. It never changes `state`, so an idle application keeps its stage, stays in its own Kanban lane, and can still move anywhere. Rejected and closed applications are never idle — they are finished, and counting them would mark every old rejection and drown the signal. Because `null` covers both "moved recently" and "finished", do not read it as "fresh"; ask `classifyLifecycle` when the difference matters.
- `describeIdle` is the only place Idle phrasing is built, the way `describeDue` is the only place date phrasing is built. The Kanban card and the table's Activity column both read it, so two views cannot describe the same silence differently and the column filter still matches its own rendered text.
- The Kanban card marker reads Idle. It previously read "Untouched N days" from `updated_at` at 14 days and applied to rejected cards too; that was an undocumented fourth rule and is not a regression to restore. The Activity column sorts on the day count with non-idle rows null, so they sink in both directions rather than reading as the freshest.
- Activity is its own context-bar select rather than another group inside the state filter. The outcome groups could share that control because they answer the same question a single state does; idleness is orthogonal to stage, so "Interview 1 and idle" is worth expressing and one select cannot hold both halves.
- Idle never enters `urgencyFor`, the score, or band placement — the same fence preference sits behind. It is display and filtering only.
- Statistics report outcomes, not inventory. How many applications sit in each state is already a badge on every Kanban lane, so repeating it here as a nineteen-row table of mostly zeros said nothing the board had not. `src/views/outcomes.ts` is the only source for the outcome derivations and they read `state_history` exclusively: `updated_at` moves when you annotate a row, and the current state alone cannot say how far something got before it ended.
- `heardBack` is "more than one recorded state", named for what it measures rather than for what it is read as. It counts a rejection, because a rejection is a reply. `advanced` is stricter: a live stage later in `LIVE_STATE_IDS` than the one the application started in, so a move that skips stages counts, a move backwards does not, and reaching a rejected state is not progress. Both are reported, because hearing back and getting somewhere are different things and the gap between them is the interesting number.
- The stage table separates `reached`, `here` and `ended` per live stage, where `ended` counts finished applications by `furthestLiveState`. It is deliberately not a funnel and must not be asserted to fall away down the list: any state may move to any other, so a later stage can hold more than an earlier one. Stages nothing has reached are left out rather than printed as zeros, and rejected states never get rows — a rejection is an outcome of the live stage it followed.
- `here` and `ended` partition the collection: every application is counted in exactly one of them, and a test asserts the sum. `reached` overlaps both and is not part of that sum.
- Sources are grouped by their stored text. Do not fold spellings together — "LinkedIn" and "linkedin" are two sources, and canonicalizing here would be a guess about what was meant. A blank or missing source is one group, rendered as an unrecorded dash rather than dropped.
- The median takes the lower of the two middles on an even count, so the figure is always a wait some application actually had. Applications with no reply are absent from it rather than counted as zero, which would drag it toward nothing.
- Statistics also summarise ratings through `preferenceSummary`, in `RATING_CONFIG` order: per dimension how many are judged, unknown, and never assessed with the mean of the judged scores, and the rated count and overall mean as a sentence beneath the table rather than as more headline figures — they describe that table, and promoting them would put two kinds of number on one baseline at the top. This is the one place preference says something a per-row number cannot — whether a dimension reads low because you keep rating it low or because you have never looked. The per-dimension rows count what was recorded, so a dimension weighted zero still reports its judgements; only the count of rated applications and the mean follow the weights. With nothing rated the table is replaced by a plain sentence rather than a grid of zeros.
- Browser-local dates control band placement, the idle threshold, and overdue boundaries. Persisted timestamps remain timezone-qualified.
- Band placement compares browser-local calendar days, so an action earlier today is not overdue. The idle threshold is inclusive: an application exactly `IDLE_THRESHOLD_DAYS` days silent qualifies.
- Kanban pairs each live state with its `rejectedStateFor` counterpart in one stage column (11 columns, 19 labelled lanes). Pairing is derived view layout only; each state remains its own drop target. Global state filtering still shows one lane per selected state without forcing a pair.

### Accessibility and interaction

- Keep dialogs and controls labelled, keyboard operable, and focus-safe. Closing an editor should restore focus to its opener when possible.
- Native drag-and-drop must retain the accessible state-selector fallback; it is also important for touch devices.
- Confirm destructive collection changes such as import replacement and demo reset, as well as application deletion.
- Preserve responsive behavior, including horizontally scrollable Kanban columns and usable narrow-screen forms.

## Gotchas

- `src/calendar/parseIcs.ts` is a deliberate subset of RFC 5545, not an iCalendar implementation: no
  recurrence, alarms, or attendees. It reads UTC (`…Z`), named-zone (`TZID=`), floating, and date-only
  starts. A named zone is resolved through `Intl` in two passes, because the offset depends on the instant
  the offset is needed to find — that second pass is what places a time near a daylight-saving change on the
  right side of it. An unknown zone falls back to browser-local rather than guessing, and an event whose
  start cannot be read is returned with a null `starts_at` so a caller can report it instead of dropping it.
- `datetime-local` inputs represent browser-local wall time. Convert them to ISO timestamps for storage and back to local values for editing; do not parse them as UTC by accident.
- The demo uses a fixed reference timestamp for deterministic content and tests, exported as `DEFAULT_DEMO_REFERENCE`. Changing it can alter idle, overdue, and band expectations throughout the suite, including in the integration tests that pin the wall clock to it.
- The editor saves ordinary field edits before applying a state move. Keep the move mutation responsible for state history so one save cannot append duplicate entries.
- Submitting the editor currently refreshes `updated_at` even when no editable value changed. An explicit same-state move is the only exact timestamp-preserving no-op. Change this only deliberately and update its tests with the behavior.
- Import validation rebuilds canonical objects, which is how unknown fields are ignored. Avoid retaining the raw imported object.
- Invalid `data/tracker.json` or `data/demo/tracker.json` files are not overwritten on startup. The app shows an error and leaves the file untouched. Invalid file imports are also non-destructive.
- The Vite dev and preview servers also expose `/__note-edit/{applicationId}/{state}`: `POST` writes the note to `{dataDir}/editing/{applicationId}/{state}.md` and launches an editor, `GET` reads that file back, and `DELETE` removes it. Scratch files are disposable; `tracker.json` stays the source of truth and `data/editing/` is gitignored.
- `TRACKER_EDITOR_URL` takes precedence over any command: the response carries `open_url` and nothing is spawned, so the browser opens it and an editor on the machine viewing the page handles the file. This is the only arrangement that works when the app is reached over a tunnel, because a spawned process always lands on the server's host. Fill the template with `{path}`, and keep using `encodeURI` so path separators survive schemes like `vscode://vscode-remote/ssh-remote+host/abs/path`.
- Otherwise the launched command comes only from `VISUAL`, then `EDITOR`, then the platform opener. Never take a command, arguments, or path from the request. The route also refuses requests whose `Sec-Fetch-Site` is cross-origin, because it both writes a file and starts a process.
- When a command is spawned and the environment looks remote (`SSH_CONNECTION`, `CODESPACES`, and similar), the response reports the server's hostname so the UI can say where the file actually opened rather than appearing to do nothing.
- The editor is spawned detached with ignored stdio, so terminal editors cannot work: the dev server owns the only TTY. Document GUI commands such as `code`, `zed`, or the platform default.
- While a stage is open externally the external file owns it: the in-app editor for that stage is withdrawn, the client polls the scratch file, and changes commit on their own because an editor has no Save button to press. Ending the session or closing the dialog deletes the scratch file.
- The Vite dev and preview servers expose `GET`/`PUT`/`DELETE` on `/__db` to read and write the active profile's database file. `pnpm dev` and `pnpm start` use `data/tracker.json`. `pnpm dev:demo` and `pnpm start:demo` use `data/demo/tracker.json`. `DELETE` reseeds demo data only on the demo profile.
- Global filtering can intentionally hide Kanban columns and affects the collection shown by statistics.
- Tests that depend on dates should control the clock and account for browser timezone boundaries rather than assuming UTC display days.
- `src/test/app.integration.test.tsx` pins the wall clock to `DEFAULT_DEMO_REFERENCE`, the instant the demo seeds are measured from. The seeds are deterministic but a view's "today" is not, so without this the two drift apart until a seed crosses an idle, overdue or band boundary and assertions start failing on a date rather than on a change. A guard test asserts the pinning, so removing it fails with the reason. Keep any new date-dependent assertion in that file relative to the reference rather than to the real clock.
- `Date` is faked there by default, via `vi.useFakeTimers({ toFake: ['Date'] })`. Widening it to the timers used to hang every test in the file: Testing Library decides whether fake timers are running by looking for a global `jest`, vitest defines none, so its `waitFor` polled a `setInterval` nothing advanced. `src/test/setup.ts` now points that name at `vi`, which is what the ecosystem settled on and is enough here — vitest's faked `setTimeout` already carries the `clock` property the same check reads. It is inert under a real clock, so nothing changes for a test that does not ask.
- A test that takes the whole clock owes two things. It must re-pin the system time, because installing the timers afresh drops what the `beforeEach` set and the demo's idle, overdue and band dates are read off it. And it must hand user-event the same clock — `userEvent.setup({ advanceTimers: (ms) => vi.advanceTimersByTime(ms) })` — or the delays it schedules between keystrokes never fire and the typing never finishes.
- Worth knowing what this buys: it removes waiting, not work. A test that sits through `AUTOSAVE_MS` stops doing so, but the render and the queries cost what they always did. On a machine with nothing spare it will not be what makes a test fit its budget. Nothing in `src/` measures elapsed time from `Date.now()`, and `createUuidV7` takes its uniqueness from random bytes, so a frozen `Date` is safe.
- `testTimeout` in `vite.config.ts` is 15s rather than vitest's 5s, and that is a floor to keep rather than trim back. The panel autosaves `AUTOSAVE_MS` after the typing stops, so a test that waits for a write to land spends 3-4s inside one `waitFor`; against a 5s test budget that leaves about a second for the render and the typing wrapped around it, and the smoke journey has since outgrown even 15s and carries its own. The result was a suite that failed roughly one run in five on whichever long test happened to be scheduled against the others, with a bare timeout and nothing wrong. Fake timers cannot shorten these waits, for the reason given above.
- What a test in this suite spends its time on is almost never the app. A Testing Library role query walks the tree computing an accessible name per candidate, and asks jsdom for a computed style on each to decide what is visible — and jsdom answers that in milliseconds rather than microseconds, with or without a stylesheet loaded. Over a thousand-node app that dominates everything else, the render included. Scope a query to the landmark holding what it wants (`within(screen.getByRole('navigation', { name: 'Tracker views' }))`) rather than searching the page, especially inside a loop: it is the difference between walking six elements and a thousand, and it reads as the stronger assertion anyway.
- Wall clock is not a measurement on a busy machine. This one runs several editor servers, a dev server, and sometimes a second suite at once, and the same journey has measured 5s and 60s of wall for about 10s of CPU. Before treating a timeout as a regression, measure with `process.cpuUsage` and check `uptime` and whether another `vitest run` is already going — and prefer `--no-file-parallelism` to raising a budget for a machine that is merely oversubscribed.
- Two things keep that from being a daily problem, and both are in `vite.config.ts`. `vite/suite-lock.ts` runs as `globalSetup` and holds one suite run at a time across every checkout on this machine, keyed by a lock in the temporary directory; a second run waits and says so rather than halving everyone's cores. Worker count is left alone. Halving it looks right — fewer workers, a larger share of a core each — but it was tried and measured worse: the same 557 tests went from one failure to fifty-three, almost all of them timeouts, and the run from a couple of minutes to twenty-three. The likely reason is that each worker process is reused across the files it is given, so halving their number doubles what each one accumulates, and a run gets slower as it goes. Reason about this one only with a measurement in hand, on a machine that is otherwise quiet.
- The lock is an optimisation and never a gate: it takes over a dead holder's lock, gives up waiting after fifteen minutes and runs anyway, skips watch mode, and honours `VITEST_NO_LOCK=1`. Keep it that way — a lock that can strand a run is worse than the contention it saves. It only takes the lock when it can positively confirm a one-shot run, because vitest leaves `watch` undefined in watch mode and sets it to `false` for `run`, so "not watching" and "not told" look alike.
- It lives in `vite/` rather than beside the tests because that is the TypeScript project carrying `types: ["node"]`. Anything under `src/` that reaches for `node:fs` and friends will not typecheck, which is also why a test that wants the stylesheet imports `../styles.css?raw` rather than reading the file.
- `vitest.browser.config.ts` runs `src/**/*.browser.test.tsx` in Chromium, Firefox and WebKit through `@vitest/browser-playwright`, for the questions jsdom cannot answer: it has no layout and applies no media queries, so where a pane ends up, whether it is still wide enough to read, and what a narrow window does to a split are all unanswerable there. It is a separate config rather than a Vitest project so `pnpm test` is undisturbed, and it is not in the four-command handoff list — run it when changing the panel's layout, dragging or resizing, the way `pnpm test:smoke` is run for navigation and persistence.
- That suite must never reach a server. `/__db` reads **and writes** the user's real `data/tracker.json` — a GET alone rewrites the file when the document normalises — and there is no data-directory override to point it somewhere safe. Three things keep it away, and all three should stay: the tests mount `StageNotesPanel` directly with stub callbacks so nothing loads or stores; the browser config's plugin list omits `trackerDbPlugin`, so an escaped request 404s instead of writing; and `src/test/setup.browser.ts` stubs `fetch` to throw. Never drive "Open in Editor" there either — that route spawns a real editor process.
- `setup.browser.ts` is deliberately not `setup.ts`. Most of what that file does is stand in for something a browser has, and stubbing `matchMedia` in a browser would defeat the one test that asks whether a media query applies. What it does carry is `styles.css`: the suite measures layout, and without the real stylesheet there is nothing to measure.
- A drag is only drivable in a browser if it is built on pointer or mouse events. The pane divider and the tab drag both are, so both are tested there. **The Kanban card drag is still HTML5 drag-and-drop**, which means it works with neither a finger nor a test: a synthetic mouse does not start a native drag session in any engine, so `dragstart` never fires and the call hangs. Moving it to `useTabDrag`'s approach would fix both at once, and is the obvious follow-up. Playwright Test would not help; it is the same automation underneath.
- Do not click with the mouse before a drag in a browser test. Playwright's WebKit swallows the `pointerdown` of the first press after a `userEvent.click` in the same test: the drag arrives as `pointermove, pointermove, pointerup`, nothing is picked up, and it reads as a WebKit bug in the drag rather than as the driver. Chromium and Firefox send the press either way, so it shows up as one engine disagreeing. Reach the same state from the keyboard — every drag here has a keyboard equivalent, which is the rule anyway.
- How a drag is told from a tap differs by pointer, and has to. A mouse commits on distance, so a press that does not travel stays a click. A finger commits on time, held still for `TOUCH_HOLD_MS`, because the gesture a swipe along a strip of tabs most resembles is scrolling that strip — a finger that moves first is left to the scroller, and one that waits picks the tab up. This is what every native list-reorder does, and it is why the strip stays scrollable by touch instead of needing `touch-action: none`.
- The drag finds where it is over by hit-testing the document, not by hover handlers on each drop place: a captured pointer sends no enter or leave events, and a capture is exactly what a drag has. So the drop places are named by attributes (`data-drop-slot-*`, `data-drop-edge`) that `document.elementFromPoint` can find. `.panel__group-body` exists for the same machinery — the edge zones are measured from it rather than from the whole pane, because measured from the pane they covered the tab strip too, and a drop aimed at a tab found an edge instead.
- `vite/machine-preflight.ts` runs as the browser suite's first `globalSetup`, before the lock, and says what the load is per core before anything has been waited for. It only waits when the machine is in the state that actually breaks a browser — around thirty times its core count, where Firefox could not be reached at all — because this laptop idles near nine times and the suite passes there. Like the lock it is an optimisation and never a gate: it gives up waiting, never refuses, and honours `VITEST_NO_PREFLIGHT=1`.
- The browser suite's budgets are measured, not guessed: `connectTimeout` is three minutes because launching a browser and rendering a bare heading measured 106s in Firefox on this machine, and `testTimeout` is two minutes because the first test pays for the panel's first paint and measured 39s with three browsers starting at once against 3s alone.
- Test setup mocks `/__db`, `/__attachments`, and `/__note-edit` with in-memory stores, seeds demo data, and supplies a `ResizeObserver` stub. `src/test/noteEditStore.ts` lets a test stand in for the external editor by writing the scratch file directly. Add new browser API stubs centrally so component tests remain consistent.

## Working on a change

1. Read the relevant domain function and its tests before changing a view that depends on it.
2. Add or update focused tests for domain behavior, derived view behavior, and user-visible integration flows as appropriate.
3. For a meaningful UI flow change, update the smoke test or `SMOKE_TEST.md` checklist.
4. Before handing off, run:

```sh
pnpm verify
```

which is `typecheck`, `lint`, `test` and `build` in that order, stopping at the first failure — cheapest signal first, so a type error does not cost you a test run. `pnpm test` already includes the smoke test; `pnpm test:smoke` runs it alone, which is worth doing while iterating on first launch, navigation, application editing, state movement, persistence, or reset behavior.

`pnpm verify:all` adds the browser suite on the end. Run it when a change touches layout, the stylesheet, or anything the panel measures, and before handing off a branch. It is separate because it is the expensive one: three engines, a machine-wide lock, and a budget sized for a loaded laptop rather than for the code. A red browser suite on this machine is as likely to be contention as a regression — re-run a failure before believing it.
